# Automatic retention behavior

See [intent](intent.md) for the outcome and authorization.

- AC1: Existing stores have no policy and delete no history. A revision-protected library policy supports optional integer maxAgeDays from 1 through 36500 and maxCompletedRuns from 0 through 1000000. At least one threshold is required when enabled. Null disables. Workflow policies replace the library policy entirely; omitted override inherits, null disables. Policies are local operational settings, separate from published definitions and portable exports.
- AC2: The library count pool includes root trees whose workflows inherit the library policy. Each enabled workflow override has its own pool. A completed tree means every member has terminal completed, failed or cancelled status. Count orders trees newest first by whole-tree last update, then root ID. Protected terminal trees count toward the limit, but never force removal of otherwise retained newest trees. Age expires only when every member was last updated before the cutoff. Either exceeded threshold makes a tree a candidate. Detached descendants and chains remain indivisible.
- AC3: The existing engine pump checks once per hour, immediately after a configuration change or when a persisted deadline is overdue after restart. Each sweep deletes at most 100 eligible roots atomically through the existing preview and confirmed deletion path. Remaining candidates retry after one minute. Failed sweeps retain history through transaction rollback, record a bounded diagnostic, and retry after one hour. No overlapping scheduler or standalone timer is introduced.
- AC4: All existing cleanup protections remain: active members, ancestry gaps, claims, resources, uncertain operations, local/background jobs, managed execution, comparisons/evaluation evidence and pending lifecycle delivery sources. Recent terminal trees have a one-minute observation window before automatic deletion; pending trigger outcomes remain protected until observed. Durable start tombstones and trigger receipts survive. Cleanup never stops work or mutates workflow definitions, policies or archived status.
- AC5: Settings API, existing grouped history MCP tool and CLI offer settings, configure and bounded status reads without adding tools. Settings expose exact scope, revision, policy and inheritance. Status exposes deadline, last sweep totals, errors and SQLite allocated/reusable bytes, never payloads. Concurrent setting updates reject stale revisions. Unknown workflows reject.
- AC6: UI offers library and workflow controls using existing settings patterns. The mode is Disabled/Enabled at library scope and Inherit/Disabled/Override at workflow scope. Age/count inputs are optional but one is required when enabled. Explain permanent deletion and the entire-tree effect beside Save. Loading, save progress, inline error/reload and saved state are visible. Native inputs keep labels, keyboard interaction and modal focus behavior; controls stack on narrow screens. Settings change immediately and do not require workflow publication.
- AC7: SQLite deleted pages are reclaimed for reuse and reported. Retention never runs VACUUM, truncates a database or claims physical file shrinkage. Offline compaction remains documented separately.
- AC8: Required docs describe opt-in defaults, scope/override/count/age/scheduling/safety/storage semantics and verified CLI/MCP examples. Patch changeset describes user-visible retention. Tests cover scheduling/restart, safe exclusions, transactional failure, count/age/overrides/defaults and file-backed reusable pages; transport checks discover and execute settings/status operations over HTTP and stdio.

The numerical bounds, hourly sweep with bounded catch-up, whole-policy override and terminal-tree count interpretation are routine implementation choices under the explicit unattended authorization. Policies may erase reports and historical usage once unprotected. No data-loss confirmation is needed for each scheduled sweep after the operator deliberately enables and saves a policy.
