# Webhook behavior

The outcome and scope are defined in [intent](intent.md). Source requirements are #240 and parent #223 M1.

- AC1. Webhook configurations share trigger identity, revision-checked CRUD, disabled creation/import, enable checks, workflow pause gates, failure auto-pause and attention with schedules. Schedules retain their existing behavior.
- AC2. Every saved webhook requires an enabled Secret reference for enablement, HMAC SHA-256 or SHA-512, a signature header and optional literal prefix. Material consists of the exact raw body or ordered body/header parts separated by a literal delimiter, supporting timestamp.body and delivery.timestamp.body. Delivery identity and event timestamp must each be in the signed body or explicitly signed header. Unsigned configurations cannot save.
- AC3. A signed timestamp is mandatory, parsed as ISO, Unix seconds or Unix milliseconds. Reject invalid signatures, stale or future event times outside the configured validity window. Stable delivery receipts prevent repeated side effects and reject conflicting signed delivery IDs. Match filters use structural equality of body/header paths. Unmatched events return 202 Ignored, increment a counter and retain no payload.
- AC4. Start actions bind input, externalTask and active-task policy and use a deterministic request key from the signed delivery ID through ordinary run-start admission. Input actions match externalTask plus exact nodeId in the trigger workflow to exactly one current waiting execution. Reject zero or multiple matches and event times before its startedAt. Submit a revision through the existing input API; existing acceptance and pause holds remain authoritative. Cancel and hold actions address active matching external tasks in that workflow. Hold means external-input acceptance hold, preserving the existing two-phase input contract.
- AC5. Raw request bodies have a configured bound of at most 1 MiB. Fixed-window per-trigger request rate limits apply before expensive verification. Persist at most 200 outcome-only delivery rows per trigger with counters and bounded errors. Logs never contain raw payloads, headers, signatures or secrets. Idempotency receipts remain separate from trimmed logs.
- AC6. POST /hooks/:triggerId is available locally and through optional --hooks-port on a separate externally reachable listener. That listener mounts only the hook endpoint, without UI, health, events, tRPC or MCP. The primary listener remains 127.0.0.1 with its host/origin checks. Unknown endpoints return 404.
- AC7. UI, CLI, shared API and MCP support webhook management and paginated delivery inspection. Portable exports carry disabled configuration and Secret requirements, never values, receipts or logs. Required README, architecture, variables and current-limits documentation describes signing, listeners, time boundaries and holds.

## UI proposal

Use the existing workflow Schedules area as Triggers, retaining schedule forms and cards. Offer Schedule or Webhook when creating. A webhook configuration editor uses the existing JSON editor with an example and server-owned validation, plus existing save, enable, disable and delete controls. Inspection shows endpoint, state, ignored count, rate limits, Secret identity and paged delivery outcomes. Preserve dirty edits on validation/revision failure. Reuse modal focus/keyboard behavior, responsive stacked layout, loading/error alerts and empty states. No payload preview is added. Human visual review is deferred by the coordinator's explicit authorization.

## Decisions and risks

General ordered signed parts support provider formats while requiring coverage of identity/time. Optional headers used in mappings remain authenticated only when included in material; docs explain this distinction. Persistent delivery receipts prevent replays after log trimming. Shared admission owns start semantics. Input submissions remain pending until explicit acceptance, consistent with #207. Arbitrary provider verification schemes and payload retention are out of scope. No material questions remain.
