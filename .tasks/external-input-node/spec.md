# External-input node specification

See [intent](intent.md) for the outcome and approved hold scope.

## Acceptance criteria

| ID  | Behavior                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| --- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| AC1 | A node with `kind: "input"` and one default route enters a durable waiting state when reached. It creates no assignment, lease, timer, or attempt budget. The node's output contract describes and validates the submitted value, which becomes its output on acceptance. The existing node input contract describes the value arriving from the prior workflow step.                                                                                                                                                                      |
| AC2 | Submit takes the exact owning `runId`, `executionId`, JSON `value`, nonblank `requestId` up to 120 characters, and optional `expectedRevision`. The first revision is 1. Each new valid submission replaces the pending value and increases the revision by one. Revision 0 means no submission. An unmet precondition, invalid value, or closed execution rejects without a state change.                                                                                                                                                 |
| AC3 | Repeating a submission key on that execution with the same JSON value returns its original receipt, even after replacement, acceptance, cancellation, or restart, for retained history. Object key order does not change identity. A different value with the same key conflicts. Check known replays before checking current revision or eligibility. The receipt includes execution identity, revision, and submission time.                                                                                                             |
| AC4 | Accept takes the exact execution identity and required `expectedRevision`. It atomically records acceptance, completes the node, and persists the next workflow position with the accepted JSON value. Stale revisions, an absent value, and cancelled waits reject. Repeating acceptance of the already accepted revision returns the same receipt. Downstream work advances once.                                                                                                                                                        |
| AC5 | Hold and release take a run ID and its hold revision. Effective holds follow the [approved scope](intent.md#decisions). Multiple holds apply independently, so releasing one still leaves any other applicable hold in effect. Submissions continue during holds. Acceptance rejects while held and stays explicit after release. The hold applies to external-input acceptance, and existing Agent work holds retain their behavior.                                                                                                      |
| AC6 | Status reads expose the execution's wait or terminal state, revision, wait start, submission time, and acceptance receipt. An explicit option returns the latest pending value while waiting, with no value before submission. The owning run's hold revision is readable. Run inspection and bounded briefings show why the step is waiting, its wait start, and its pending revision. Briefings omit pending values. Run change cursors wake for submission, holds, release, acceptance, and cancellation that change the observed wait. |
| AC7 | Loop visits and Batch items have distinct execution identities. A command for a different run or earlier visit cannot affect the current wait. Restart preserves receipts and pending state. Cancellation closes the wait. History cleanup removes this run's external-input records. Workflow exports carry only the definition.                                                                                                                                                                                                          |
| AC8 | The shared HTTP API, CLI, and MCP expose status, submit, accept, hold, and release. Group MCP operations in one tool. Mutation responses are receipts or hold state. Document discovery from run briefings, exact revision acceptance, and recovery by replay or status read. Explain that adapters own source authentication and acknowledge outside systems after verifying an acceptance receipt.                                                                                                                                       |
| AC9 | Existing workflows and Agent execution retain their behavior. The editor, portable definitions, and run graphs recognize the node. Both MCP discovery transports advertise the new contract and keep ordinary run and assignment summaries bounded.                                                                                                                                                                                                                                                                                        |

## Editor and run inspection

Add **External input** to the existing node type selector. Use the existing contract editor for the submitted value's schema. Label that section **Submitted value**. A short hint explains that the step pauses and that the accepted value passes to the next step. The existing input editor remains available for optional workflow context.

In the run inspector, use the existing selected-step panel. Show **Waiting for external input**, **Revision N pending**, or **Acceptance on hold** as applicable. Show the wait start and use the existing copy affordance for identifiers if available. Completed and cancelled visits use the ordinary status treatments. The first UI increment covers authoring and inspection. Integrations and operators use the shared API, MCP, or CLI to submit and accept.

Keep the node selector, contract controls, and step inspector keyboard reachable with existing focus behavior. Use the existing stacked panel layout on narrow screens. Reuse the inspector's loading and error states. Missing submissions show the waiting state without an error.

## Reconciliation example

Submit a staging decision as revision 1. Submit a correction as revision 2. Accepting revision 1 fails. Accepting revision 2 commits the value and returns its receipt. If the response is lost, inspect the same run and execution or replay acceptance for revision 2.

See [issue #207](https://github.com/dgca/interlock/issues/207).
