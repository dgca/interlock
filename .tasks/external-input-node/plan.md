# External-input node implementation plan

Use the [intent](intent.md) for scope and the [specification](spec.md#acceptance-criteria) for behavior. Work on `codex/external-input-node` at the baseline recorded in the intent.

## Build sequence

1. Add the node and grouped operation contracts in core. Reuse the default-route graph validation and node contracts. Keep revision fields and receipt identity typed. Keep request schemas strict and mutation results compact. (AC1, AC2, AC4, AC8, AC9)
2. Add a runtime module for submission, acceptance, status, and holds. Reuse canonical JSON fingerprinting for submission identity. Keep immutable submission receipts and the latest pending payload in run-owned documents keyed for exact lookup. Keep revision and timestamps on the node execution and hold state on the selected run. Use the execution's retained acceptance metadata for replay. Include new documents in history inventory and deletion. (AC2–AC7)
3. Integrate the node in Engine's waiting and completion paths. Put eligibility checks, accepted receipt state, output, and cursor change in one store transaction. Pump after commit. Use existing cancellation and restart rules, and derive hold inheritance from the same ordinary-parent boundary as cancellation. Project effective holds in inspection and briefings. Use scoped continuation revision updates to wake waiting descendants when ancestor holds change. (AC1, AC4–AC7)
4. Add shared server operations, one grouped MCP tool, and a CLI command. Use a read-only status query and shared mutations. Point run discovery guidance to the new operation and keep submitted values behind the explicit read. (AC6, AC8, AC9)
5. Add the node to the editor, graph, and run inspector. Reuse the contract editor and step status patterns. Update README, current scope, architecture, authoring, execution, CLI and MCP guidance, and a patch changeset. (AC1, AC6, AC8, AC9)

## Build verification

| Risk                                                        | Direct check and expected result                                                                                                                                                                                                                                                                                                                                                                                  |
| ----------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Lost or conflicting delivery (AC2–AC4)                      | Submit a valid control, replace it, and replay the first submission. It returns the first receipt while status stays on the replacement. Reuse the key with a different value, use a stale revision, and submit invalid JSON against the contract. The pending revision, value, and receipts stay unchanged. Accept the current revision and replay it. The same receipt comes back and downstream executes once. |
| Partial acceptance (AC4)                                    | Inject a storage write failure after acceptance writes begin. Compare run, receipts, pending value, and downstream state with the pre-request snapshot. Retry without the injection and verify successful acceptance.                                                                                                                                                                                             |
| Inhibition and run isolation (AC5–AC7)                      | Hold a root with attached and detached waits, then submit corrections. Verify attached waits reject acceptance, detached waits can accept, and releasing a child hold cannot bypass a held ancestor. Check a waiting child's cursor after ancestor hold and release. Retry, cancel, and loop back through a node to exercise the exact execution identity.                                                        |
| Restart, cleanup, and portability (AC3, AC4, AC6, AC7, AC9) | Reopen a temporary database with a pending value and accepted receipts. Verify status, replay, and progress. Check that the history preview counts new documents and cleanup removes them. Export and reimport the definition and confirm it excludes the submitted value.                                                                                                                                        |
| Transport and inspection (AC6, AC8, AC9)                    | Exercise authoring, publication, submit, status, acceptance, and failure through HTTP and stdio discovery and calls. Verify the CLI command against the shared API. Check the bounded briefings omit values and identify the wait.                                                                                                                                                                                |

Run focused tests, `pnpm test`, `pnpm build`, `pnpm format:check`, and `pnpm test:package`. Use temporary databases.

### Representative UI journey

Create External input in the workflow editor, set a submitted-value contract with the existing contract editor, and publish. Start a run and inspect the waiting step. Submit a value through the shared interface and check that the inspector shows the pending revision. Accept it and check that the next step receives the value and the wait clears. Check node selection and contract controls with keyboard navigation and inspect the same state on a narrow viewport. (AC1, AC6, AC9)

## Independent review

A fresh-context reviewer checks the exact committed candidate against the acceptance criteria and project standards. Review rechecks at least one of the atomic acceptance or hold inheritance boundaries and inspects the builder's actual transport and UI evidence. Record concrete criterion evidence at the reviewed commit. Resolve material findings before delivery. After opening the verified PR, request the separate subagent review the user asked for.
