# Saved cases and paired live comparisons

Scope and authorization are in [intent.md](intent.md). This specification owns the observable behavior; implementation and checks belong in plan.md.

**AC1. Suites and cases.** MCP/shared API can list, create, read and revision-protect updates to a named suite associated with one existing workflow. A suite contains 1–25 cases with unique stable IDs, names, explicit JSON input, optional source-run provenance, assertions and optional quality guidance. Case input is at most 64 KiB; the saved suite is at most 1 MiB. A case may capture the original input from a run of that workflow, without copying its work, tokens, events, outputs or unrelated history. Missing sources and stale revisions reject atomically. Updating the suite does not change prior comparison snapshots.

**AC2. Small assertion vocabulary.** Cases hold up to 50 assertions. Output checks select the root result or one root-scope node's output at an explicit positive visit number, with dot-separated paths using the existing readPath semantics. Operators are exists, structural equals, numeric gte and lte. Route checks require a root-scope node ID, positive visit and expected port. Malformed checks reject on save. Comparison preview rejects unknown nodes, unsupported Batch-member checkpoints and nonexistent declared ports in either selected definition before execution. Batch and child runs still execute normally; arbitrary nested assertion selectors are outside this first increment.

**AC3. Check outcomes.** Each result is pass, fail or unknown with the assertion and a precise reason. A missing path on available output fails; missing/unavailable output, a node visit that did not execute, an unfinished execution or unavailable run history is unknown. An available unequal value or route fails. Existence checks succeed for a present JSON null. Numeric checks require numeric actual and expected values. Execution status/errors remain separate from assertion outcomes; unknown is never counted as pass. Reports expose counts and bounded individual checks with exact totals.

**AC4. Preview and start.** A read-only comparison preview selects a suite/revision, baseline and candidate positive published version numbers, repetition count 1–10, and concurrency 1–10. Repetitions default to one and concurrency to two. The plan shows exact root-run count, cases/repetitions/sides, captured dependency IDs/versions/hashes, prompt IDs/revisions and blockers. Maximum 100 root runs per comparison, 64 dependency pins, 64 saved prompts totaling 1 MiB, four active comparisons and ten active comparison execution trees globally. Nested runs add work under ordinary Batch and Workflow rules and are not included in the exact root count. Clearly state that runs perform real Script/Fetch actions and require connected Agent executors.

**AC5. Stable experiment.** Start requires the preview confirmation and a caller-generated request ID. Recompute the plan transactionally; changes to suite revision, definitions, prompt revisions or relevant eligibility reject the stale plan without creating runs. Repeating the same request with identical arguments returns the existing comparison; conflicting reuse rejects. Snapshot suite cases, exact pins and current saved prompt content once, including dependencies. Both sides of every case use that comparison capture for matching prompt IDs, including delayed Batch, child and detached dispatch. Ordinary runs keep their existing prompt-capture behavior. No run substitutes latest for a selected pin. In-flight/queued comparison dependencies block explicit version cleanup and workflow deletion until no longer needed.

**AC6. Ordinary execution and restart.** Queue ordinary root runs under bounded comparison concurrency, with each root's active descendants consuming its slot even after the root finishes. Use existing claim, renewal, validation, timers, retry, execution and ancestry rules. Persist planned samples, each assigned run ID, captures and progress so restart never duplicates a previously started sample. Script/Fetch interruption keeps existing inspect-before-retry behavior. Report a missing/deleted run as unavailable rather than silently reexecuting it. Suite/case/repetition/side and comparison provenance are visible through run inspection and summaries. No real provider/account is required for automated tests.

**AC7. Detached lifecycle and cancellation.** Completion waits for all comparison execution trees, including independent detached descendants, to become terminal. Report root execution errors and detached errors distinctly. Cancel prevents queued starts and cancels active roots through ordinary cancellation, preserving detached independence by default. An explicit cancelDetached option may also cancel this comparison's detached descendants. A cancelled comparison reports remaining independent active runs and their IDs until they finish; never describe cancellation of the roots as completion of detached work. Ordinary run cancellation and retry semantics are unchanged.

**AC8. Reports and quality.** MCP/shared API provide bounded comparison discovery, compact progress and a paged report with suite/revision, exact version/capture references, sample/run links, execution status/errors, check counts and check details. Reports have a 256 KiB byte cap as well as bounded pages, exact totals and continuation offsets. Previews return at most 50 blocker details with an exact blocker count. No claim tokens or arbitrary run outputs are returned in compact reports. Use existing selected-result inspection for full values. Record append-only human or agent quality judgments separately, with declared reviewer identity/kind, explicit rubric, score from 0 to 5 and notes. Do not infer quality from shape checks or automatically launch an evaluator. Distinguish score provenance and expose judgment totals. Terminal sample observations remain snapshots; later explicit retries do not silently rescore earlier evidence. Missing underlying history is explicit. No automatic publication or promotion occurs.

**AC9. History and retention.** Suites, captures, sample observations and judgments persist across restart. Source-run provenance is informational; captured case input survives source-run deletion. Definition cleanup may remove terminal comparison graphs under its existing informed-agreement policy; retained comparison observations remain available and identify missing run history when applicable. Deleting the associated workflow removes its suites/comparisons as well as its ordinary guarded run history; active comparison pins block that deletion. Portable workflow bundles do not include local test cases or comparisons in this increment. Updating or importing definitions never rewrites comparison captures.

**AC10. Small UI changes.** Existing global and workflow Runs rows show comparison name or short ID, case name, baseline/candidate side and repetition for comparison roots and detached runs. Run inspection shows the same context and a link to its paired counterpart when available. Keep the existing title, graph, results, errors and navigation. Labels wrap on narrow screens, use existing components and add no new focus behavior except the ordinary counterpart link. Loading/missing counterpart state omits that link. No new suite editor, comparison dashboard or start controls are added. Ordinary runs render as before.

**AC11. Compatibility and guidance.** Keep existing run APIs and definitions compatible through optional comparison metadata. Follow storage migration guidance, using compatible document collections/readers where no conversion is needed. Update domain terms, README, architecture, current limits, harness and agent guidance, relevant CLI help and affected MCP authoring/execution/cleanup flows. HTTP and stdio discover identical strict schemas, bounds/defaults and lifecycle guidance. Add a pending patch changeset for the public root package.

## Decisions and alternatives

Revisioned suites plus immutable comparison snapshots let a user repair a case without rewriting earlier evidence. Reusing the existing path notation avoids introducing another query language. Root-scope assertion selectors provide useful checks while making unsupported nested expectations explicit.

Capture current shared prompts once for each comparison so queued samples remain comparable. This evaluates the two published definitions using one disclosed prompt-library snapshot; it does not claim to recover the prompt library as it existed when either definition was published. A future historical-prompt selection is separate scope. Reports identify the exact capture.

Detached cancellation follows ordinary run semantics unless explicitly requested otherwise. Tracking detached trees until terminal preserves useful completion and concurrency accounting without changing ordinary run rules. Preview counts roots exactly and discloses that nested execution increases work.

No unresolved specification decisions remain. These choices implement the accepted bounded, live, MCP-first comparison and preserve existing lifecycle rules.
