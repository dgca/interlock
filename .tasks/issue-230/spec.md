# Pause behavior

See [intent](intent.md) for scope and authorization, and [UI design](ui/ui-design.md) for the settled presentation.

- AC1: Each pause creates a persistent UUID record with scope library or workflow, optional workflowId only for workflow scope, trimmed nonempty actor and reason, and createdAt. Actor is descriptive, not authentication. Exact-ID resume releases only that record; replaying release is harmless and never selects another record.
- AC2: A run is paused by any active library hold or hold naming its workflow ID. Batch item runs share their workflow identity. A hold does not automatically apply to independently invoked workflows with a different ID. Holds combine by union and progress requires zero applicable records. Historical released records retain intervals for active-time calculations.
- AC3: Paused runs cannot acquire claims, launch managed Agents, create the next step, dispatch child work, start Script/Fetch operations or polling checks, or advance waiting steps. A running Agent/Script/Fetch/check may finish and record its result. Its following step stays blocked. Existing leases continue to require renewal and resource ownership remains unchanged.
- AC4: External-input submissions and revisions remain available while paused. Acceptance rejects with an actionable pause reason and creates no acceptance receipt. Replaying an acceptance already committed remains idempotent. Clearing pauses does not implicitly accept pending data.
- AC5: Reads, navigation, editing, cancellation, and cleanup remain available. Manual starts allocate durable runs, then wait at the pause gate. Pause and resume use the shared server API across UI, CLI, and MCP. Bounded lists report exact totals and pagination.
- AC6: Pause records and applicable gating survive restart. Persisted overlapping intervals count once in active elapsed calculations, clipped to the queried attempt or execution. Existing unclaimed Agent timeout clocks suspend during pause. Claim leases remain ownership clocks, native in-flight operation timeouts remain operation safety bounds. Wait/poll deadlines retain wall-clock meaning and overdue waits advance only after resume. Future retry, stall, and total execution-deadline implementations consume the shared active-time calculation.
- AC7: Current stage labels remain accurate. A blocked run reports waiting.kind pause, person actor, stable since timestamp, bounded hold details and count. Actively finishing work keeps its actual stage and actor. Lists, inspection, briefings, compact results, events, and UI agree.
- AC8: Follow the UI handoff: persistent library row, workflow header action/banner, shared focus-trapped dialog, required blank actor/reason fields, independent add action, complete hold details, and row-local exact-ID release confirmation. Indicate remaining holds, preserve mutation inputs on failure, keep last known state on refresh failure, announce errors/count changes, restore focus, and fit desktop and 390px widths. Pause controls are separate from workflow save/publication and input-specific holds.
- AC9: Required docs explain current operations and exact-ID safety. Schedules, webhook queue policies, doctor, retry windows, stall monitoring, and total Agent execution deadlines remain explicitly future capabilities.

These criteria derive from #230/#223 and the existing UI authorization. Technical choices use existing document storage, engine ownership, Mantine components, and transport conventions. No unresolved product decision remains.
