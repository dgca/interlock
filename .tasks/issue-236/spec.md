# Schedule behavior

Authority: [intent.md](intent.md), live #236 and #223, and [UI handoff](ui/ui-design.md). This is progression under existing authorization, not human approval.

## Acceptance criteria

- S1: A durable `workflowTriggers` record with `kind: schedule` supports revision-protected create, update, enable, disable and delete through shared API, UI, grouped MCP and CLI. Create defaults disabled. Draft workflows can retain disabled schedules. Enable requires an unarchived target with a retained latest published version. Each fire captures that version.
- S2: Interval accepts integer milliseconds at least 30000. Its creation/timing-change instant anchors slots. Cron accepts exactly five fields and a valid IANA zone, using cron-parser for grammar and DST. Macros, six-field seconds and hashed jitter are rejected. Preview returns three server-calculated UTC instants with the selected zone. Shared validation rejects invalid timing, binding paths/collisions, policies and JSON input.
- S3: Default overlap is skip. Any active or queued run from this trigger suppresses a skip fire. Queue accepts at most one queued run from the trigger, waiting for prior active runs to become terminal regardless of success. Workflow capacity and public success dependencies remain independent gates. Allow starts additional runs subject to workflow admission. Changes never cancel existing runs.
- S4: Default missed policy is skip. A scheduler gap beyond five seconds marks overdue slots as missed. Skip advances to the next future slot. Run once attempts only the latest overdue slot, then advances to the future. Normal sub-five-second tick delay fires the due slot. No replay burst after sleep, downtime or scope pause. Enabling skip advances overdue slots without firing. Enabling run once can make one recovery attempt. Timing changes re-anchor and discard old due slots.
- S5: A fire, its input, captured published version, deterministic request ID `schedule:<triggerId>:<slotIso>`, run receipt and next-slot update commit atomically under the Store transaction. Concurrent engines and restart cannot create two runs for one slot. Bindings map scheduledAt, firedAt, triggerId and previousRunId to explicit dot paths, replacing literal template values. previousRunId is null before the first accepted run. Run-start retries use captured input and version, not a new firedAt.
- S6: Library/workflow named holds prevent scheduled starts and admission promotion. Held slots follow missed policy on recovery. Schedule disable stops future starts and preserves active/queued runs. Re-enable clears only automatic pause and resets its failure counter. It never releases named holds.
- S7: Run failures do not disable by default. Optional positive integer pauseAfterConsecutiveFailures pauses after that many observed failed scheduled runs or failed fire admissions. Completed scheduled runs reset the counter, cancelled runs and policy skips are neutral. Terminal runs are observed once, in fire order within a tick. A visible automatic-pause reason appears independently of run attention. Excessive lag means at least 60000 ms between scheduled slot and actual admission, or enabled overdue next slot. Lag alerts never disable. Normal successful on-time fire clears lag. Queued fire history distinguishes acceptance time from eventual admission time.
- S8: Inspection exposes last/next slot, measured lag and threshold, failure count, effective named holds, automatic pause and bounded paged recent fire outcomes. Started/queued are admission outcomes, separate from run completion. Missing/deleted run history remains inspectable. Schedule attention counts independently of run rows, appears in Runs Needs attention, links by stable trigger ID and uses accessible wording “items”.
- S9: Portable bundles carry schedule configuration without operational history and with enabled false. Import always disables included schedules, validates identity/workflow ownership and never enables through force. Older bundles still import.
- S10: UI follows the chosen Mantine handoff, responsive at 1440/900/390. Inspection is primary. Editing has Timing, Run input and Policies; literal JSON and explicit bindings. Pending mutations block duplicate edits/dismissal. Save rejection retains values. Acknowledged save plus failed refresh closes editing and offers read-only Retry refresh without repeating the write. Conflict retains edits. Exact enable/disable/re-enable/delete actions name schedule and ID. No run-now or bulk release.
- S11: Documentation updates cover CONTEXT, architecture, v1 limits, README, CLI help and affected MCP workflow, including exports and starts/pause inspection. HTTP and stdio discovery expose consistent bounded contracts. A patch changeset describes shipped behavior. Deterministic tests cover DST, validation, gaps, holds, overlap, competing stores, restart, atomic rollback, failure pause and attention independently of run history.

## Technical decisions

Use cron-parser rather than a custom timezone iterator. Current primary docs from https://github.com/harrisiirak/cron-parser/blob/master/README.md and CronExpressionParser API, retrieved with find-docs/Context7 2026-11-07, confirm parse/currentDate/tz/next/prev and DST support. Library strict mode requires six fields, so validate exactly five first and use ordinary parser semantics. Disallow nondeterministic H expressions. DOM/DOW restrictions retain standard parser OR semantics and are documented.

Fire logs retain at most 200 settled rows per trigger plus unresolved admitted runs, with pages capped at 100. Deleting a trigger removes its fire log, never existing runs or RunStarts receipts. Operational records have independent revisions from workflow drafts. Future webhook/event kinds are not exposed prematurely.
