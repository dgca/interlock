# Background Script behavior

The [intent](intent.md) owns scope and authorization. These requirements follow issue #224 and parent #223 H2.

- AC1: Script nodes accept opt-in `executionMode: "background"`. Omission and `"foreground"` retain the current runner. Polling Script checks retain their existing restart behavior. Language and timeout contracts remain unchanged.
- AC2: Persist a launch intent bound to the run ID, execution ID, and unpredictable execution token before launching. A local detached supervisor starts the Script once, owns its process group and deadline, and writes a durable terminal outcome. A server shutdown leaves background work running. Repeated startup/pump reconciliation must neither replay work nor advance an execution twice.
- AC3: Reconnect only to the original supervisor identity, checked against OS process start identity and the execution token. A matching durable outcome is recoverable even after the supervisor exits. Missing, corrupt, mismatched, or unverifiable evidence marks the execution uncertain and fails terminally without a failure route. Recovery requires an explicit operator confirmation that the original process and effects have been inspected before retrying. Never signal an unverified PID.
- AC4: The supervisor enforces the original absolute deadline offline. Run cancellation and an explicit stop action stop the Script process group through the verified supervisor. Normal execution errors, deadline errors, and output-contract failures use the existing optional Failed envelope. Cancellation and uncertainty remain terminal.
- AC5: Inspection exposes mode, lifecycle state, deadline, supervisor identity and bounded recent stderr progress, without credentials or raw input. JavaScript console output is stderr. stdout remains a single JSON result with the current 1 MiB limit. Inspectable progress is at most 8 KiB. Secret-consuming Scripts use existing redaction before any logs/results enter run metadata; their durable raw data is encrypted and launch credentials remain in memory or owner-only transient input. Fail closed when protected data cannot be recovered.
- AC6: Existing shared API, CLI and MCP inspection/cancel/retry paths describe background recovery. Add one bounded grouped Script operation for inspect, stop, and explicit uncertainty reconciliation, shared by API/CLI/MCP. Reconciliation records an operator reason and stopped confirmation, never fabricates success or reruns the old execution.
- AC7: Tests cover restart while running, offline completion, offline deadline, cancellation including descendants, identity mismatch/missing evidence, secret masking and repeated recovery. Cover JavaScript, legacy Bash, result validation and failure routing.

The editor adds a Background execution switch beside the existing timeout. Its description explains survival across server restart. The run inspector uses existing execution details for bounded background state/progress. Stop and recovery remain explicit operational API actions; existing Cancel and Retry actions retain their positions. Keyboard and responsive behavior follow the existing controls.

Risks: host loss and destructive spool deletion leave an uncertain outcome. This mode requires a file-backed store and same local user/host. It does not promise transactional external effects or survive removal of its supervisor. An outcome committed in SQLite is the acceptance boundary; durable receipt recovery is idempotent against that execution ID.

No material questions remain. Encryption, launch handshake and process identity are technical choices to validate during implementation.
