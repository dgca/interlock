# Security

Interlock is a trusted local tool for one person. Workflows run Scripts, Fetch requests and agents with your user account's access, so treat a workflow like code you run.

- The engine defaults to `127.0.0.1`. The [operator settings](cli.md#operator-config-file) `host` and `publicUrl` select the listen address and advertised origin. The desktop listener stays on `127.0.0.1`. Interlock rejects unexpected request hosts and browser origins. Hosted use remains unsupported pending sign-in and the HTTPS check. Do not expose the port through a public tunnel, proxy, port forward, or container port mapping.
- The startup link uses the internal URL. For a wildcard listener, that link uses loopback and opens on the engine machine. If a specific bind address or custom port changes the local endpoint, set `INTERLOCK_URL` for CLI commands and the stdio bridge.
- Interlock creates a per-install [API token](connect-harness.md#api-token) in an owner-only `api-token` file. The UI, the `interlock` CLI and the stdio bridge send it automatically, and **Connect with MCP** includes it in HTTP client configuration. The engine requires the token on `/api`, `/trpc`, `/mcp` and `/events` when the listener or configured public hostname is off loopback. To require it for other configurations, set `requireToken` or `INTERLOCK_REQUIRE_TOKEN=1`.
- The operator config is read-only through the UI, API, MCP, and CLI. Apply changes on the engine host and restart. A file that declares `allowedRoots` prevents edits to the shared roots through executor settings. These settings do not restrict filesystem access that the operating system grants to Scripts or harness commands.
- Scripts are not sandboxed. A Script's [server environment](architecture.md#scripts-and-interruptions) mode decides which of Interlock's environment variables it receives. `minimal` passes only `PATH`, `HOME`, locale variables, `INTERLOCK_*` variables, bound saved variables, execution context and the names you list to pass through. Scripts and polling checks added in the editor start in `minimal`. A Script without a mode, or set to `inherit`, receives the whole server environment, including any credentials in it, so existing and imported workflows keep their behavior.
- Managed agents run at **Default agent permissions** (AI Settings → Execution settings) unless a harness or workflow sets its own level. While no default is chosen, that level is **Full access**. **Full access** removes the harness sandbox and approval prompts: agents run commands and edit files with your account's access without asking. Choose it only for repositories and workflows you trust. See [permission levels](managed-executors.md#choose-permissions).
- Imported Scripts wait for [one-time approval](reuse-work.md#approve-imported-scripts) before their first run. Scripts you write, or that a connected agent writes over MCP, run without approval unless you extend approval to agent-authored Scripts. Review imported Scripts before you run them. Import review also shows each imported workflow's agent permission level; a workflow that sets none runs its managed Agents at your default, which is Full access until you choose one.
- Managed Claude Code sessions load your user, project and local Claude Code settings, including the MCP servers configured there. If Interlock is connected to Claude Code, a managed session can use every Interlock MCP tool that connection exposes. Pi sessions likewise keep their own MCP connections and extensions.
- Claude Code, Codex and Pi sessions that Interlock launches get two tools of Interlock's own: `save_memory_note` and `call_workflow_tool` (see [memory](https://github.com/dgca/interlock/blob/main/docs/memory.md#managed-sessions-save-notes) and [agent tools](https://github.com/dgca/interlock/blob/main/docs/agent-tools.md#managed-sessions)). Interlock runs each call itself against the claim it holds for the session. The session, its hooks, other MCP servers and the commands it runs never receive a claim token or other credential, in the prompt, the environment or the transcript. Saving is write-only and limited to the session's step and workflow. The tools are off at **Read only**, and run without an approval prompt at **Standard** and **Full access**. `call_workflow_tool` runs the Script or Fetch steps that the workflow's author attached to that Agent as tools. A Script runs in the Agent's checkout, with its own [server environment](https://github.com/dgca/interlock/blob/main/docs/architecture.md#scripts-and-interruptions) mode and no sandbox, using arguments the Agent chooses within the tool's input schema. Attaching a tool is the author's grant: under **Standard** there is no prompt per call, as for connected agents calling `call_work_tool`. This is the one way an Agent at **Standard** runs code without being asked. Imported Scripts still wait for their one-time approval. In Pi the call travels to Interlock as an extension dialog with a private name, and a call skips approval only when Pi reports the tool as registered by Interlock's extension; other installed Pi extensions run in the same process and are trusted like any code you install. In Claude Code the tools count as Interlock's only once Claude Code reports Interlock's own server connected; a server you configure under the name `interlock_assignment` is not trusted. In Codex the calls arrive over the app-server connection Interlock owns, and only calls naming the session's own thread are answered.
- On loopback, while the API token is optional, any local program that can reach the server can call the whole API. That includes a managed session that can run commands or has Interlock's MCP server configured. For example, it can approve its own pending memory notes through `memory manage`. The `interlock` CLI reads the API token file, so a session with access to that file keeps the same access when the token is required. Require the token to stop programs that cannot read it, and run untrusted workflows at **Read only**.
