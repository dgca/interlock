# Managed Agent execution

Interlock can launch installed Claude Code and Codex harnesses when an Agent assignment becomes ready. The execution manager runs inside the existing server. Keep Interlock running; no separate worker or open chat is required. Connected MCP agents and manual completion remain available.

## Configure a harness

Open **Harnesses** in the sidebar. Interlock checks for `claude` and `codex` on the server's PATH and reads their version. **Detected** means an executable answered the version check, not that authentication or model access works. Checks make no model calls. Install and authenticate the harness using its supported native setup before starting work. Interlock does not collect credentials, install harnesses, or promise that every subscription supports unattended third-party execution. See [Claude Agent SDK authentication](https://platform.claude.com/docs/en/agent-sdk/overview) and [Codex authentication](https://developers.openai.com/codex/auth/).

Default configurations start disabled. Configure the working directory, optional model and default permissions, then enable the profile. An omitted directory uses the server's working directory. Executable and directory overrides must be absolute paths. Advanced settings include declared tools/skills already available in the native harness. Capability declarations do not install tools or provide containment. Multiple configurations can use the same harness.

Harness rows summarize their saved model and permission defaults. **Configure** groups the editable fields into execution defaults and **Advanced settings**. **Configuration ID** is the stable reference workflows and MCP use; renaming the configuration does not change it. **Available tools** and **Available skills** declare existing capabilities for matching Agent requirements and do not install them. The detected native version appears with the executable path. Refreshing installation details preserves an open form’s edits; **Cancel** or **Cancel editing** discards them. Failed saves retain edits and offer **Reload configuration** to replace them with the saved values.

In **Workflow settings**, choose a **Default Agent executor** and **Agent permissions**, then save and publish. **Use harness default** inherits each selected profile’s default. An explicit **Read only**, **Standard** or **Full access** choice overrides the default for all managed Agents in this workflow, including node-specific executor selections. Connected agents retain their own permissions. The effective mode and its source appear beside the executor selection and in execution details. Agent **Execution → Executor** can inherit that default, choose another profile, or require a connected agent. In JSON, workflow `executor` is a profile ID. Agent `executor` overrides it; `null` selects connected-agent execution; omission inherits the workflow default. Workflow `agentPermissions` stores the optional override as `read-only`, `standard` or `full-access`; omission inherits the harness default. The published assignment captures the override, and later edits do not change existing attempts. Existing definitions without these fields keep their behavior. Missing, disabled or incompatible profiles leave work unclaimed with a reason. Executor references and workflow permission overrides travel in exports; local profile paths, defaults and native sessions do not.

Batch items use their owning workflow’s settings; invoked workflows use their own published settings. Agent permission modes do not restrict Script or Fetch execution.

The manager discovers ready assignments globally, including work started by scripts or in detached workflows. It uses the existing exclusive claim path, so a connected worker and managed harness cannot own the same attempt simultaneously. Budgets, shared resources, output validation and retry limits still apply. Managed local Git trials remain blocked because these adapters do not implement the scoped-tool containment contract.

## Choose a model

Harness **Default model** offers **Use CLI default**, models reported by the configured native harness, and custom model IDs. Open the picker to load its list; **Refresh models** bypasses the cache. Discovery initializes the native integration without sending a user prompt or starting an Agent turn. It uses the configured executable and working directory, including unsaved path edits in harness settings, and never claims work. Authentication and native startup policy still apply. Claude discovery disables ordinary hooks and configured MCP servers; administrator-required hooks can still run.

The picker reads Claude Code's SDK `supportedModels()` and Codex's app-server `model/list`, rather than a generic provider catalog. Lists can vary with the installed version, account and project configuration, and do not guarantee a later request will succeed. Catalogs return at most 100 models and cache for five minutes; failed reads cache for 30 seconds. Discovery is bounded to 15 seconds plus process cleanup and version detection. Failures preserve the saved model; refresh or enter a custom ID. No fallback model is substituted by Interlock.

Workflow **Agent model** offers **Use harness default** or an explicit model ID, stored as optional `agentModel`. The override applies to every managed Agent in that workflow, including node-specific executors. If those use different harnesses, choose an ID they all accept or leave the model inherited. Connected agents retain their own model. Batch items inherit their owning workflow; invoked workflows use their own setting. Publish to apply changes to new runs. Published assignments capture the override as `executorModel`; retries and continuing sessions retain the resolved profile/model. Effective model and source appear in settings and execution details. The workflow override travels in exports; model catalogs and local profile defaults do not. Existing advisory model tiers remain separate.

## Sessions and permissions

Ungrouped assignments start independent native sessions, including retries. A `current` assignment permits existing context; it does not inherit the conversation that started the workflow. A run-local `context.continuityGroup` reuses a manager-owned native session and serializes work in that group. `fresh` always starts independently and cannot use a continuity group. Existing externally bound groups are not silently adopted.

The profile is captured at first claim, retained on retries and pinned for a continuity group. Later profile edits affect unbound work. The actual native model, when reported, is recorded alongside the resolved executable and directory. Advisory model tiers do not automatically select native models in this release.

Claude Code uses the official Agent SDK with the installed executable and native user/project/local configuration. Codex uses its app-server protocol. Both retain native project instructions and supported authentication. **Standard** follows native permission rules; actions already allowed by native rules may proceed without an Interlock prompt. Interlock forwards requests that reach the host and does not persist broader permission grants. **Full access** explicitly selects Claude’s `bypassPermissions` with SDK bypass enablement, or Codex’s `danger-full-access` sandbox with `never` approvals. It permits file changes and commands without routine approval stops. Native deny rules, mandatory questions and organization restrictions still apply. **Standard** maps to Claude’s default mode and Codex’s workspace-write sandbox with untrusted-command approvals. Codex Read only uses its read-only sandbox without permission escalation. **Read only** restricts supported native tools, but does not isolate project startup hooks or make an untrusted repository safe.

Open the run inspector to answer a pending permission or question. **Allow once** or **Deny** applies to that exact active request. Native Codex additional sandbox-grant requests, session-wide file grants, secret-input requests and MCP elicitations are declined in this release. File approvals require captured paths and patches; incomplete approval details are declined. Questions allow custom answers only when the native request supports them. Human answers must come from the user, not another agent's guess.

Progress records contain bounded tool/status updates, not full conversations. Native output and error text can contain task data; use non-secret task inputs. Interlock records reported usage where available. Missing measurements stay unknown. Resumed cumulative counters are differenced when a baseline is known; uncertain resumed history is not charged again. Provider cost estimates are not account billing.

## Stop and recover

**Execution details → Stop execution** asks the native process to stop. Cancellation, a disabled profile, claim loss, server shutdown or restart can leave external effects uncertain. The assignment is held where possible, and another claim is blocked. Pending questions become cancelled.

Interlock attempts bounded process-group cleanup for both adapters, including children whose parent has exited. This is not an operating-system sandbox; assignments must stop their own background work before returning. Stop the old session and any surviving subprocesses, inspect external effects, then explicitly confirm that they stopped in the inspector. Reconciliation releases uncertain resource reservations and resumes held work with a fresh claim. It does not revive a cancelled run. Deleting history is blocked while managed execution is active or uncertain. Do not confirm merely because a lease expired or a process disappeared from Interlock.

**Concurrent assignments** at the top of Harnesses offers **Limited** with a positive whole-number limit, or **Unlimited**. The default is Limited to 3. There is no eight-assignment ceiling. Unlimited starts every ready managed assignment that meets the normal execution requirements; resource coordination, continuity and workflow sequencing still apply. Additional assignments wait for capacity. Raising the limit can start queued work immediately. Lowering it lets active assignments finish and delays new starts until there is room. Workflow settings show the shared limit and link back to Harnesses. There are no per-profile or workflow overrides and no additional hidden concurrency cap. Assignments waiting for human input still occupy a slot. Connected agents, manual claims and Batch item-path concurrency retain their existing behavior. In MCP/API settings, `concurrency` is the positive numeric limit or `null` for Unlimited; zero is invalid. The setting stays local and persists across server restarts; it is excluded from workflow exports. Retired per-profile concurrency values from earlier draft builds are ignored. Interlock imposes no maximum runtime on managed Agent assignments, including time waiting for a human. Claims renew before expiry; they are ownership leases, not task deadlines. Native harness and provider limits still apply. Existing Script/Fetch execution timeouts and optional unclaimed Agent deadlines retain their behavior. Explicit completed native failures and invalid results consume the existing failure budget. Transport loss and unexpected adapter errors hold the assignment for reconciliation; no unbounded repair loop is added. There are at most 20 local profiles and 100 human requests per execution. Inspection returns the latest attempt, up to 20 recent progress entries, pending requests and the last three resolved requests, plus at most ten compact older-attempt records.

## MCP and CLI

One `manage_executors` tool handles these operations through the shared server API. The CLI accepts the same request JSON with `interlock executors`, defaulting to read-only list. Examples:

```sh
interlock executors
interlock executors '{"action":"settings"}'
interlock executors '{"action":"save_settings","concurrency":3,"expectedRevision":0}'
interlock executors '{"action":"save_settings","concurrency":null,"expectedRevision":1}'
interlock executors '{"action":"list","refresh":true}'
interlock executors '{"action":"models","profileId":"codex","refresh":true}'
interlock executors '{"action":"save","profile":{"id":"codex","harness":"codex","name":"Codex","enabled":true,"cwd":"/absolute/project","expectedRevision":0}}'
interlock executors '{"action":"inspect","workId":"WORK_ID"}'
interlock executors '{"action":"respond","executionId":"EXECUTION_ID","requestId":"REQUEST_ID","answer":{"allow":false}}'
interlock executors '{"action":"stop","executionId":"EXECUTION_ID"}'
interlock executors '{"action":"reconcile","executionId":"EXECUTION_ID","confirmStopped":true}'
```

Profile `permissions` defaults to `standard`; `read-only` and `full-access` are also supported. The previous draft value `ask` is accepted and normalized to `standard` without changing saved revisions. Save replaces a profile and requires its current revision as `expectedRevision`. Omit returned `revision` and `detection` fields. Keep existing settings when updating; omitted settings reset to defaults. New and unsaved built-in profiles use revision zero. Questions use `answer.answers` keyed by exact question IDs with arrays of chosen answers. Inspection never returns claim tokens. Work discovery includes compact `executor`/`managedExecution` fields, while briefing `next:inspect_executor` supplies a read-only inspection call for human attention. Neither discovery nor inspection starts a model call.

The initial adapters target macOS/Linux installations. Native account access, enterprise restrictions and CLI version compatibility still require validation in the user's environment. OpenCode, other harnesses, Channels, remote workers, automatic permission decisions and automatic harness installation are outside this increment.
