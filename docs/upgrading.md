# Upgrade Interlock

## Install an update

1. Stop the running Interlock server with Ctrl+C. Close any other server using the same database.
2. Record the installed version with `interlock --version`.
3. Install the update:

   ```sh
   npm install -g @type_of/interlock@latest
   ```

4. Start `interlock` with the same `--db` and `--workdir` options you used before.

Interlock checks the database before seeding examples, resuming runs, or accepting requests. If a schema upgrade is needed, it creates a SQLite backup and applies all pending migrations in one transaction. Startup prints the backup path after a successful upgrade. If the backup or migration fails, startup stops with an error. A failed migration rolls back its database changes; its backup path appears in the error.

Installed copies default to `~/.interlock/interlock.db`. Development copies use `.interlock/interlock.db` in the checkout. `--db` or `INTERLOCK_DB` can select another file. Backups live beside the selected database in `<database-path>.backups/<timestamp>-v<old>-to-v<new>-<unique>/interlock.db`.

Backups are created only when an existing database needs a schema migration. Fresh databases and ordinary restarts create none. Backups remain until you remove them. Keep the backup and the previous package version until you have verified the upgrade. These snapshots cover database state, not files written by scripts or changes to external services.

Database schema 2 adds indexes for run discovery by workflow, status, and creation time. Updating a schema-1 database creates a backup before adding the indexes. Definitions, version pins, run records, and ownership remain unchanged.

Startup checks whether the configured port is occupied before opening the database. A locked database error identifies its path and suggests stopping other instances. Use `lsof -nP -iTCP:4310 -sTCP:LISTEN` to identify the listener, adjusting the port when needed. If a process was suspended with Ctrl+Z, `kill -CONT <pid>` lets it handle a pending termination signal. A separate engine needs both a different port and a different database.

## Restore a pre-upgrade backup

Restoring replaces database state with the snapshot. Changes made after that snapshot are not included. Stop every server using the database before proceeding.

1. Find the `interlock.db` backup path from the startup output or the database's `.backups` directory. Ignore any `.partial` file left by an interrupted backup.
2. Preserve the current database and any matching `-wal` and `-shm` files together in a separate directory. Do not copy a backup over a database with old sidecar files beside it.
3. Copy the backup to the original database path. Leave the backup itself intact.
4. Install the package version you recorded before upgrading, for example:

   ```sh
   npm install -g @type_of/interlock@0.1.3
   ```

5. Start Interlock with the same database path and working directory.

Interlock does not run reverse migrations. Versions with the migration guard refuse databases with a newer schema than they support. Older releases without that guard may still open newer databases, so use a matching backup when reverting to them.

## Add a database migration

The schema version is independent of the npm package version. `packages/storage/src/migrations.ts` owns the ordered migration list and the existing `migrations` table records completed versions.

Append the next consecutive version when a persisted format needs conversion. Do not edit a migration that has shipped. Keep migration functions synchronous and confined to database changes; the runner owns the transaction and version records. Do not commit transactions or perform external side effects in a migration.

Preserve immutable published definitions, version pins, and run history. Prefer compatible readers for optional fields when no rewrite is needed. A schema migration does not make an incompatible API or execution change backward compatible.

Add a fixture from the preceding release and test the conversion, rollback, and execution of its published workflows. `tests/migrations.test.ts` covers the runner using test-only future migrations, including a failed later migration and committed WAL data. Its schema-v1 fixture was generated by the tagged 0.1.3 runtime and includes JavaScript and legacy Bash workflows, published versions, completed runs, and events.

The runner uses SQLite's [VACUUM INTO](https://www.sqlite.org/lang_vacuum.html#vacuum_with_an_into_clause) to create a consistent snapshot, including committed WAL data. It checks `PRAGMA data_version` after acquiring the migration write lock and refuses to continue if another connection committed during backup. This check protects the upgrade; it does not add support for multiple running servers.
