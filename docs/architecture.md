# Architecture and execution semantics

Interlock keeps workflow behavior in the runtime so that UI, CLI, and MCP callers share the same execution rules.

## Packages

| Package   | Responsibility                                                                   |
| --------- | -------------------------------------------------------------------------------- |
| `core`    | Domain types, JSON contracts, graph validation                                   |
| `runtime` | Execution, child scheduling, work claims, context requirements, script lifecycle |
| `storage` | SQLite persistence and transaction ownership                                     |
| `server`  | Hono listener, tRPC procedures, run event stream, starter catalog                |
| `client`  | Typed HTTP client shared by UI, CLI, and MCP                                     |
| `ui`      | React application, React Flow editor, reusable controls, run inspection          |
| `cli`     | Installed server entrypoint, MCP bridge startup, JSON commands                   |
| `mcp`     | Shared MCP tools for HTTP and stdio callers                                      |

HTTP MCP invokes the server router in process. The stdio bridge uses the typed HTTP client. Both transports register the same MCP tools.

The client imports the server router type only. It does not bundle or instantiate the engine. The server is the only process that writes application state. MCP adapters and CLI commands can exit without losing runs.

SQLite stores workflow, version, run, assignment, and event documents. Since schema 21, a run document holds run fields only; each node execution is its own row keyed by run and position, and saving a run writes only the rows that changed. Each synchronous engine operation uses a transaction. The runtime reads compact run and assignment metadata when selecting candidates for advancement, dispatch, stall detection, and run lists. Storage maintains this metadata in the same transaction as the source documents. Runtime derives stage, waiting reason, and actor from current executions and attached branches. Full inspection reads scoped history, and explicit run input matching reads only candidate inputs. Budget refresh selects governing ancestors and chain members, then aggregates their retained scope. Comparison scheduling loads sample trees rather than unrelated runs. This favors a small local implementation over a distributed scheduler and does not support multiple competing server processes. History is retained by default; opt-in library or workflow retention reuses guarded whole-tree cleanup after lifecycle dispatch. Hourly bounded sweeps persist their deadline and result; large active trees, budget scopes, comparison archives, and explicit history inspection can still increase resource use.

Interlock sets `synchronous = NORMAL` when SQLite uses write-ahead logging (WAL). SQLite syncs at checkpoints and skips the disk sync on most commits. Committed transactions survive an Interlock process crash, but a system crash or power loss may roll back recent commits. Interlock sets `synchronous = FULL` outside WAL mode. See [SQLite's synchronous pragma](https://www.sqlite.org/pragma.html#pragma_synchronous).

The root `@type_of/interlock` package bundles the server, CLI, and MCP code into `dist/cli.js` and copies the built UI into `dist/ui`. Private workspace packages are implementation modules. Changesets versions the root package; CLI, UI, and MCP versions come from `packages/core/src/version.ts`, which reads the root manifest. See [Release Interlock](releases.md).

Server startup does not install workflows. The bundled catalog in `packages/server/src/starters.ts` exposes bounded choices through the shared API, UI, CLI and existing MCP list/import operations. Explicit starter imports publish a new copy without running it; a default import can return a known existing copy unchanged. New request keys plus `copy:true` deliberately create additional copies. The additive `starterCopies` collection retains local identity through later edits, while `starterImports` atomically records keyed import results. Identical retries recover their copy; conflicting keys and deleted results reject. Legacy recognition compares current drafts and retained definitions without canvas positions or declaration order, never just a display name. Portable exports exclude local tracking. The templates are bundled in the installed CLI; no network or checkout is needed. See [starter behavior](starter-workflows.md).

GitHub folder discovery runs in the server using bounded public API requests for metadata and commit-pinned raw GitHub file downloads. Core parses existing import documents. Runtime validates each export in an isolated in-memory store and imports the selected set through one storage transaction. Discovery pins a branch to a commit; import re-fetches only selected direct files at that commit and checks current conflicts. Typed transport failures stop discovery; invalid files produce individual diagnostics without hiding valid choices. Confirmed import rejections carry a `Nothing imported:` prefix. A lost response without that confirmation leaves the mutation result uncertain, so the UI advises inspecting the library before retrying. This path has no force or revision replacement options. The existing bundle import API retains its explicit replacement controls.

## Read query review

For new or changed inspection, history, and collection reads, trace retrieval through runtime into storage. Identify the selected scope, payload size, and work performed before response limits apply. A page-size limit does not bound a query that first loads and parses unrelated history.

Use indexed metadata to select relevant records before loading payloads. Keep aggregates within their requested scope and preserve existing ordering, totals, ancestry, and response contracts. When a query must inspect a whole scope, state that cost explicitly.

Add regression coverage with substantial unrelated retained history. Prefer assertions about records retrieved or payloads parsed over wall-clock test thresholds. Use separate benchmarks to measure latency. Reuse existing storage queries where their semantics match.

## Run version boundaries

Core owns version policy, preview/apply, and bounded history contracts. Runtime checks opt-in upgrades before creating a node execution, resolves the proposed node's input with the same binding rules as execution, and requires retained prompt, variable, and model-alias captures. A missing node, incompatible input, or changed Batch or chain scope leaves the run on its old version with an inspection blocker. Existing active executions, including available Agent work and active Batch dispatch, finish using their original definitions and routes.

Explicit apply rechecks a preview confirmation transactionally and persists the binding and timestamped reason together. Prompt recapture is explicit and obeys target publication pins. Each new execution stores its version. Run-local policy and change records stay outside portable workflow bundles. Version cleanup protects actual active bindings and future dependencies, while its impact includes historical executions of removed definitions. UI, CLI, and MCP use the shared server operations. See [run version behavior](workflow-execution.md#move-a-run-to-a-newer-version).

## Workflow definitions

A workflow has a stable ID, mutable metadata, and an editable draft. Publishing validates graph routes, JSON schemas, and child version references, then creates an immutable version. Draft revisions reject stale edits. Runs read their bound published version, including when the workflow is renamed or its draft changes. The default version policy is pinned; publishing alone does not change a run.

The shared `workflows.edit` operation applies stable-ID node, edge, and settings edits in order to a copy, checks the expected draft revision, and commits once. Core owns the edit vocabulary and diagnostic collector. Runtime adds persisted child-reference and version checks within the storage transaction. Equivalent edits retain revision and timestamp. Save errors reject the transaction; incomplete graphs remain saveable. `workflows.validate` provides read-only draft or candidate diagnostics, separating save errors, publication blockers, and conservative contract warnings. An optional summary diagnostics projection compares warnings before and after the edit within that transaction, retaining errors and newly introduced warnings across the graph. Full diagnostics remain the default. Neither operation publishes or starts a run. See [agent editing](agent-workflows.md#edit-a-draft-atomically).

One entry begins a run. Each node receives the previous node's forwarded output unless input bindings construct its input. An ordinary node has one default outgoing route unless it opts into result routing. Conditions have one true route and one false route. Switch nodes have one route per named case and an optional named fallback route. Agents with `unclaimedTimeoutMs` retain a timeout route in addition to their configured success routes. Exit nodes have no outgoing route. Workflow-level back-edges can target upstream nodes other than Entry. The same run re-executes those nodes, with each visit counted against `maxSteps`. Batch item paths must be acyclic.

Agent, Script, Fetch and waited Workflow nodes may configure `routing` and `outputBindings`. Runtime validates `outputSchema` and Agent result rules against the raw operation result, selects the result port, then constructs the forwarded output. Input/output bindings share literal values, nested object construction and missing-path defaults; original run/item inputs remain immutable. `execution.output` remains forwarded data; mapped steps retain the raw accepted result in `execution.result`. Storage removes both payloads from continuation metadata. Bounded result reads opt into `field:"result"` with an execution ID. Legacy definitions and omitted fields keep their behavior. See [Step data and result branches](node-data.md).

A condition compares a path in its input to a JSON value using structural equality. It passes the input through unchanged. Paths are dot-separated object keys or array indices. Empty paths select the entire input. They are not general JSONPath expressions.

A Switch compares the same kind of path against an ordered case list using structural JSON equality. The first match selects its named port; no match fails the run unless an optional `default` port specifies a fallback route. A missing path fails the step. Switch passes its resolved input through unchanged, including input bindings, and validates its output contract on every route. Case and configured fallback port names must be nonblank and unique at publication, with exactly one outgoing edge each. Omitting `default` requires no fallback edge. Empty case lists are allowed and always take the unmatched action after resolving the path. Port names are local to the source node: names such as `item` and `timeout` do not trigger Batch or Agent behavior on Switch. Executions persist the selected `port`. See [Switch routing](switch.md).

A Workflow node invokes an existing published workflow version once. Optional `mode` is `wait` or `detached`; omission retains wait behavior. Detached dispatch validates the resolved input against the referenced workflow before atomically creating a child and completing the launching execution with `{runId, workflowId, version}`. Empty output contracts use the intrinsic run-reference contract; conflicting overrides block publication. A nested storage savepoint rolls back child creation if dispatch completion fails. See [Workflow execution](workflow-execution.md). It can reference its own workflow ID, but the pinned version must already be published. A new version can therefore invoke an older version of itself, not its own unpublished definition. A Batch selects an array from `itemsPath` and repeats a visible item path for each value. A blank path selects the complete input. Each value becomes the complete input of an isolated item run. The Batch collects item results in input order, even when items finish out of order. Empty arrays produce an empty result.

### Owned child workflows

Workflow records carry optional `ownerWorkflowId` metadata. Missing or null ownership means a library workflow. An owner must be a library workflow. Core reference validation permits only the owner to reference an owned child in a saved draft or published version. This authoring rule does not change execution ancestry or the existing ten-level run limit.

`createChild` atomically creates the child and saves the parent's name, description, and draft with an expected draft revision. An optional node ID identifies the new reference. Failure rolls back both records. Workflow nodes accept null versions in drafts; publication and execution reject unresolved pins. `useChildVersion` checks the parent revision, ownership, target node, and published version before updating the parent draft. Ordinary publication never automatically advances parent pins. Opt-in cascade publication follows latest published references transitively, including archived dependents and Workflow nodes inside Batches. The runtime publishes in dependency order within one storage transaction and advances only references to workflows in that cascade. Dependents must have no unpublished definition edits. Cycles or validation failures roll back every publication. Dependent draft revisions advance with their pins. Older definitions remain unchanged. Existing runs remain unchanged unless their own opt-in version policy later accepts an upgrade at a safe boundary.

The library filters out owned workflows, while the app retains all workflow records for direct route resolution. Library workflow pages add a Child workflows tab at `?view=children`. The tab uses a centered, bounded card grid with descriptions, publication badges, step counts, draft usage, and a deletion menu. Active and Archived controls and search filter the parent's children. New child opens a naming dialog before saving the parent and navigating to the child. Child pages link to their owner; node actions open the target's existing resource route. Creation saves parent edits before navigation. Children retain separate editors and run histories. Direct starts reject archived children and children of archived parents; existing published invocations retain the prior archive behavior.

This authoring increment blocks clone and deletion of parents with children. Portable export includes owned children, owners, and dependencies. Ownership moves use shared `workflows.previewOwnership` and `workflows.setOwner` operations. Preview lists foreign drafts and all retained published callers with node locations. Set requires the expected current owner, rechecks references transactionally and updates only ownership and the workflow timestamp. A target with children cannot become a child, and a new owner must be an active library workflow. Release to null relaxes reuse restrictions. No-op preserves timestamp and draft revision. Moves preserve definitions, cleanup identities, active assignments and execution ancestry. Complete parent clone/deletion operations remain unimplemented. Ownership is not editable through Raw JSON or generic metadata updates. The list interface accepts owner and archive filters while preserving unfiltered calls for existing clients.

### Batch handles and graph scopes

A `batch` node owns `itemsPath`, `maxItems`, `concurrency`, and `failurePolicy`. Its ordinary input receives the incoming value, and four handles control the flow:

| Stored handle | UI label | Direction       | Behavior                                                |
| ------------- | -------- | --------------- | ------------------------------------------------------- |
| `default`     | In       | Input           | Receives the incoming value before selecting items      |
| `item`        | Start    | Internal output | Starts the item path once per selected value            |
| `end`         | End      | Internal input  | Finishes one item with the connected step's output      |
| `complete`    | Out      | Output          | Emits the ordered collection after all item runs finish |

The workflow stores all nodes and edges in one flat definition. A member node's `batchId` identifies its direct owning Batch; absence means the main workflow. Positions are relative to that owner. An edge's `port` selects its source handle; optional `targetHandle: "default"` selects the ordinary input, as does omission. `targetHandle: "end"` returns a member step's output to its owning Batch. Every item branch must connect to End; a disconnected step is an incomplete draft.

Item paths can contain Agent, Script, Fetch, Wait, External input, Condition, Switch, Workflow, and nested Batch nodes. Each Batch has exactly one `item` route into its direct members. Ordinary routes must remain within the same group. A Batch's `complete` route continues in its enclosing scope; a nested Batch can connect its Out handle to the enclosing Batch's End. Conditions require both branches, each leading to End. Every Switch case and any configured fallback branch must also reach End. An unmatched value without a fallback fails the item and follows the Batch failure policy. Membership is explicit graph data, independent of node positions or overlap. Validation rejects missing owners, circular membership, unreachable members, cross-group edges, Entry or Exit members, and cycles within item paths. Ordinary workflow loops outside item paths remain bounded by the workflow step limit.

Drafts may have missing routes or incomplete paths. Visual and Raw views report graph errors, and publication validates all routes, contracts, scopes, and referenced versions.

### Persisted item runs

Item runs use the existing scheduler, script runner, assignments, events, and cancellation. Their `workflowId` and initial `version` identify the same immutable published graph as their parent Batch execution. An item can independently opt into a compatible version at its own step boundaries; the owning Batch scope must remain valid. A `batchNodeId` identifies the owning Batch. An item run starts at the destination of `item` and completes when a step follows an edge into that Batch's `end` handle. Returning an item never advances the parent's output route. No generated workflows or copied definitions are stored. Inspection and restart resolve the published graph with its original handles.

A Batch allows 1 through 50 concurrent item runs. Its optional `maxItems` is an integer from 1 through 10,000 and defaults to 200 when absent, including in older published versions. The runtime checks the selected array length before dispatching any items. Oversized input fails with the actual count and limit. Each nested Batch applies its own limit; this is not an aggregate cap on descendant runs. Larger limits increase persisted history and local resource use. Each item run has the published workflow's step budget, independent of its parent and siblings. `maxSteps` defaults to 100 and permits 2 through 1000. Each node execution counts once, including Entry, Exit, repeated visits, and explicit retries that create a new execution. Waiting and claim retries within an existing execution do not spend extra steps. A Batch counts once in its parent. An item step-limit failure reports the limit and node; the parent reports how many items completed. Batches and referenced workflows share the limit of ten nested child-run levels. A referenced Workflow node starts a child run at the referenced version's entry with its own workflow contracts. Batch input and output contracts apply to the aggregate input and collected output; ordinary item-path nodes validate their individual inputs and outputs.

The `all` policy fails the Batch and cancels unfinished items when an item fails or is cancelled. The `collect` policy emits one record per item with `runId`, `status`, `output`, and `error`; missing output and error values are `null`. Node contract failures belong to their item runs. Explicit retry of a failed Batch preserves completed items and resumes failed or cancelled items within the concurrency limit. Individual item retries also wait for a free slot. A completed `collect` Batch is a successful step and is not eligible for failed-step retry. Cancellation stops unfinished descendants and invalidates their work claims. Root-run work discovery includes assignments in every nested item path.

Permanent deletion removes a workflow, its versions, and its run trees, including descendant assignments and events, in one transaction. Active runs and references from other workflow drafts or published versions block deletion. Both active and archived workflows can be deleted after confirmation in the UI.

### Batch output

The `complete` port emits an array in input-item order. Its shape depends on `failurePolicy`:

- `all`, the default, emits raw item outputs, such as `[{"answer":42},{"answer":7}]`. If any item fails or is cancelled, the Batch fails without emitting a collection.
- `collect` emits one record per item, including failed and cancelled items:

```json
[
  {
    "runId": "item-1",
    "status": "completed",
    "output": { "answer": 42 },
    "error": null
  },
  {
    "runId": "item-2",
    "status": "failed",
    "output": null,
    "error": "Unavailable"
  },
  { "runId": "item-3", "status": "cancelled", "output": null, "error": null }
]
```

A collected status is `completed`, `failed`, or `cancelled`. `output` is the item's final run output, or `null` when absent. It does not contain partial node results from a failed item. `error` is the run error string, or `null` when absent. A completed item can also return JSON `null`, so use `status` to distinguish success from failure.

For `collect`, downstream nodes read each record's `.output` after checking `.status`. For `all`, they read each array element directly. Both policies emit `[]` for an empty input array. The Batch output contract validates the whole emitted array.

### Parallel groups

A Parallel group owns a fixed list of branch identities and result keys. Members declare `parallelId` and `parallelBranchId`. Each `branch:<id>` source port enters its own path, and `targetHandle: "join"` returns to the group. Publication checks membership, reachable members, return boundaries, and cycles. Outer workflow routes can revisit the group. Parallel and Batch cannot be nested together inline.

Each group execution starts ordinary child runs on its captured version. The parent stores child links in branch order, and each child stores its branch identity and exact parent execution ID. Branches inherit the parent prompt, variable, and model-alias captures. Session bindings and node/execution bindings remain local to each branch. `runInput` retains the owning workflow's original input. Group inputs carry data needed from upstream steps.

Branch runs share workflow admission. Each new branch step charges the owning run's `maxSteps` in the same transaction as its execution record. The group itself counts once, and Join has no separate step. Called workflows retain their limits. Budget scopes and detached boundaries apply as for ordinary descendants.

The group validates and forwards a named result object only after every branch succeeds. On failure, the runtime cancels unfinished waited branches. Optional `joinAfter` and `onBranchFailure` make a partial join: core `decideJoin` completes the visit once enough branches succeed, and the runtime cancels the remaining branch trees in the same transaction, recording the join in each cancellation reason and `cancellationKind: "join"`, which reports leave out of run outcomes. Partial joins output `{results, branches}` with per-branch status; groups without the settings keep the keyed result object. Retry uses the existing invocation and keeps completed branch outputs. Uncertain external work requires stop confirmation before retry. Briefings expose bounded `parallels` counts and named branch references in descendants. See [authoring and recovery](parallel.md).

## Agent work

Optional node input bindings select incoming data or original persisted workflow, root, and Batch item inputs, the latest completed output of a node in the current run (`source: "node"`), or engine-verified execution provenance (`source: "execution"`), before input validation. Both `node` and `execution` bindings can set `sourceDefault` for absent completed executions and `default` for a missing path within an available execution. Resolved inputs appear in execution history. See [input bindings](agent-workflows.md#bind-original-input-into-later-steps) for scope and retry semantics.

### Execution provenance and anti-spoofing

When a node completes execution, the engine evaluates 1-based `visitCount` within the current run and Batch scope and collects verified executor attributes (`profileId`, `harness`, `sessionId`, `requestedModel`, `actualModel`, `provider`, `effort`, `attempt`, `visitCount`, `startedAt`, `endedAt`, `usage`). Provenance is assigned directly to `execution.provenance` by the engine and cannot be spoofed, overwritten, or modified by worker submission payloads. Downstream nodes bind provenance via `source: "execution"` or evaluate `execution.<nodeId>.<path>` in standalone Branch conditions. Foreground and background scripts receive prior node provenance via `INTERLOCK_EXECUTION_PROVENANCE_FILE`.

Provider attribution uses reported provider identities when available, then model/profile metadata and known model-name prefixes. Optional executor settings `providerPrefixes` override prefix attribution. This metadata does not restrict which providers may execute a step.

The editor derives optional input hints from draft edges and declared contracts. Explicit node input contracts take precedence. Bindings yield a projected object shape; pass-through nodes can carry an inferred shape forward. Conflicting incoming shapes and unknown source contracts yield no single hint. These hints drive editor suggestions only. They are not stored, do not affect publication, and do not change runtime contract checks unless the author explicitly copies a hint into a node input contract.

Work and run summaries derive `workflowId`, optional `parentRunId`, `rootRunId`, and `rootWorkflowId` from persisted run ancestry. Root runs identify themselves with their root IDs and omit `parentRunId`. Summary queries cache shared ancestors within each request and read ancestor identity without loading execution history. No root fields need to be backfilled into stored runs. Detached children add `parentMode: "detached"` and `parentExecutionId`; ancestry and `rootInput` keep their original meaning. Cancellation stops at detached relationships. Detached children can be retried directly after the parent ends, and later parent retries do not repeat completed dispatches. Fresh-context instructions stop their ancestor walk at the nearest detached run. Global Runs shows detached runs alongside roots, while `rootOnly` query semantics remain unchanged. Existing JSON records need no schema migration.

Run discovery uses schema-2 indexes for workflow, status, and creation order. Arbitrary input-path matching iterates the filtered candidates. The scheduler still scans run history; query indexes do not remove that scheduling limit. Portable bundles preserve workflow IDs and published definitions; transactional imports reject version conflicts and require a revision map or force option for draft replacement. See [agent workflow operations](agent-workflows.md).

Agent nodes persist an assignment and pause. A worker claims available work with an expiring token. Agent nodes may set integer `leaseSeconds` from 10 through 3600. The assignment captures this optional setting from the run's published definition. Claims use an explicit duration override, otherwise that setting, otherwise 300 seconds. The claim persists its effective original duration as optional `claimLeaseSeconds`. Omitted renewals reuse that duration, falling back to 300 seconds when the field is absent. Explicit renewal durations affect only that renewal. Claims check the requested fresh-context mode, required tools, and required skills against worker declarations. The assignment includes the exact prompt, input, context policy, and output contract.

Results must satisfy the output schema. Read-only preflight and submission share the core result-contract evaluator. Preflight never pumps timers or writes state; submission recovers overdue leases and rechecks inside its transaction. Structured rejection reports distinguish correctable contract errors from unusable claims. See [result preflight](result-preflight.md). Invalid results leave the claim active so the worker can correct them. Repeating an accepted result with the same token is idempotent. A changed duplicate, stale token, or cancelled claim is rejected.

The manual UI keeps minimal claim credentials in an application-lifetime memory store, separate from assignment bodies. It preserves them across client-side navigation, updates their expiry on renewal, and removes them on expiry, successful submission, or observed invalidation. Panels subscribe to credential changes; expiry timers also run with no panel mounted. Startup removes recognizable legacy session-storage claims without restoring their tokens. Reload loses the credential and leaves the server lease unchanged. See [manual claim recovery](connect-harness.md#manual-claims-in-the-ui).

A reported failure or expired claim makes work available again until its budget is exhausted. Without `maxLeaseExpiries`, both consume the combined attempt limit. With this optional per-Agent limit, `failureCount` is checked against `maxAttempts` and `leaseExpiryCount` against `maxLeaseExpiries`; either limit fails the run when reached. Claim `attempt` remains monotonic. Work captures the published policy and persists both counters. Each processed expired claim records `work.lease_expired` with the work ID, deadline, attempt count, and recovery guidance. Existing retry and failure events still apply. Bounded hashed expiry receipts support actionable stale-token errors and are excluded from work responses and continuation metadata. Expiry processing commits before a claim-sensitive operation reports an error. Expired tokens cannot renew or submit results; increasing the lease does not change this rule. Manual retry starts another attempt sequence and records that intervention. A step budget still bounds execution within each run.

Optional Agent `context.continuityGroup` binds a declared `{executorId, sessionId}` within one exact run ID. First binding and immutable claim history commit with the claim; replacement requires a revision-checked handoff with no active group claim. Runtime owns enforcement; storage retains bindings and claim/handoff records in additive document collections. Available work carries the current binding, while attempted work and history retain their captured identity. A run context revision wakes continuation readers even when no assignment is available. Child runs never inherit bindings. See [context continuity](context-continuity.md) for scope, recovery, and bounds.

Context requirements are a cooperation contract with the executor. Interlock cannot prove that an external harness created a fresh conversation, restrict that harness's other tools, or erase its history. No native MCP sampling callback is required. Work discovery and submission implement the return path.

Core defines bounded Agent resultRules and structural evaluation. Runtime captures rules with assignments and checks them against captured resolved input through the shared preflight/submission evaluator before completing work. Rejected results retain a valid claim for correction. See [result checks](result-preflight.md#check-results-against-assignment-input).

Runtime external holds preserve one assignment and its captured input while invalidating active claim authority. Separate interval records support bounded history and declared blocked-time accounting. Resume returns to availability through existing claim/budget/context checks; cancellation closes the interval. Holds do not stop external processes or replay actions. See [external holds](work-holds.md).

## Saved prompts

Core defines prompt content, optional Agent `promptIds`, and pure instruction composition. SQLite stores current prompts and immutable revision records in document collections; Run `promptSnapshots` and assignment `savedPrompts` are compatible optional fields requiring no migration. Runtime protects edits with revisions, reports usage across drafts and every published version, and blocks deletion while references exist. Missing references are publication diagnostics; incomplete drafts remain saveable.

Each workflow invocation captures the latest prompts referenced in its own published graph at startup. Batch items and Parallel branches inherit the enclosing capture, including delayed dispatch. Invoked workflows, including detached work, capture independently when they start. Loops, claim recovery, retries, and restart retain that run's captures. Workflows can opt into `pinPromptsAtPublish: boolean`: publishing a workflow version pins the exact current `revision` of referenced prompts into immutable `WorkflowVersion.pinnedPromptRevisions`, and runs capture those exact pinned prompt revisions instead of floating to latest saved revisions. Saved prompt sections precede node task instructions. Context policy and contracts retain their meanings. Compact storage projections omit captures and saved instruction bodies.

Bundles with published prompt pins use format version 9 and include the exact required historical snapshots in `promptRevisions`. Import retains history without rebinding identical current prompt content, rejects historical identity conflicts and unavailable pins, and keeps later edits above retained revisions. Model-alias-bearing bundles use format version 6 with named requirements without local overrides. Format 10 preserves authored alias IDs as `reference` requirements bound to local names. Runtime retains known alias requirements separately from local candidates, including after deletion; unresolved requirements reject startup before work. Empty run captures preserve literal model IDs against later alias creation. Schedule-bearing bundles use format version 5. Variable-bearing bundles use format version 4 with safe requirements and deliberate local binding. Other bundles with deleted version identities use format version 3. Other prompt-bearing bundles use format version 2, including current shared prompt records from exported drafts and all versions; other prompt-free bundles retain version 1. Exported versions preserve `pinnedPromptRevisions`. Import preserves IDs, reuses identical local content, and rejects divergent shared content even with force. CLI `interlock import` supports `--dry-run` to preview semantic diffs against published definitions (ignoring layout positions and key order) without mutating the database, and `--publish [--cascade]` to atomically import and publish workflows in dependency order inside a single transaction. Re-importing a deleted prompt allocates a current revision above retained local history, preserving old revisions and subsequent edits. Truly new IDs retain the bundle revision. Unrelated revision history and run captures are excluded from workflow bundles.

The Prompts library and editor use the shared Mantine theme and navigation protection. Dirty prompt text retains its original save revision across external refreshes. Agent settings provide searchable ordered prompt selection and content inspection above Task instructions. Run inspection shows captured content and revisions.

## Workflow variables

Variables have instance-wide identities, case-insensitively unique names, immutable
Config or Secret kind, metadata edit revisions, and separate value revisions.
Direct portable bindings associate imported IDs with same-kind local variables.
Bindings cannot chain or override a value-owning identity. Ordinary list and inspect
operations return metadata only; an explicit Config read returns ordinary values.
Secret read-back is unavailable. The shared API is `variables.read` and
`variables.manage`; MCP exposes two grouped tools with bounded discovery and
dependency pages. See [variable management](variables.md).

Storage encrypts both kinds with AES-256-GCM. Each database's vault identity and
authenticated value envelopes live in SQLite; the random 256-bit key lives in a
separate owner-only file. Authentication binds the vault, variable, kind, and value
revision. A retained authenticated vault verifier rejects wrong-key writes even
after value records are deleted. Metadata reads expose the local key location for backup and recovery,
never the key or value envelopes. Default key paths and `INTERLOCK_SECRET_KEY_FILE`
are described in the management guide. The first value creates a key lazily;
workflows without variables require none. Missing or invalid established keys are
never regenerated. The file backend supports local macOS and headless Linux; it
does not isolate the running server from its OS user. Encryption-key rotation is
not implemented.

Run `variableCaptures` retain only portable and local identities, name, kind, and
value revision. Ordinary workflow runs capture their own graph at startup. Batch
items and continue-as-new successors inherit. Invoked workflows, including detached
children, capture independently. Comparisons capture at most 64 transitive
references and 1 MiB of values before queueing; both sides and descendants use
those protected revision references, included in safe configuration identities and
reports. Arbitrary historical per-side variable selections are unsupported. A
workflow supports at most 64 distinct references. Metadata edits preserve value
revisions; replacement allocates a new revision. Revision numbers are not reused
after deletion and explicit provisioning of the same portable identity.

The native operation path resolves only referenced Fetch headers and Script
environment entries, including polling checks. Persisted Fetch requests and
previews retain safe references. Fetch requests that reference a Secret stop at
redirects. Script inputs and Agent assignments do not receive
injected values. Disabled, deleted, missing, or inaccessible exact revisions fail
without empty or latest-value fallback. Existing captures are checked again at
consumption. Simulation substitutes operations without resolving live values.

Known delivered Secret occurrences are scrubbed in returned strings,
object keys, scalar results, and errors before contract validation, result routing,
failure routing, history, or forwarding. This includes forms trimmed during HTTP
header normalization, URL-encoded, JSON-escaped, Base64, and standard Node
diagnostic representations. HTTP failure classification uses the
actual response status before redaction. Matching covers overlapping representations
before inserting masks. A matcher failure or more than 10,000 matches in one string
replaces that entire string with the mask. Secret-consuming Scripts redact complete bounded stderr before
retention truncation; excess diagnostic output fails safely. A result that no
longer satisfies its contract fails using the safe result. This protects against
accidental disclosure, not arbitrary transformations, partial values, or
disclosures by trusted code outside Interlock. Literal credentials and unrelated
host environment secrets are not automatically recognized.

Old encrypted revisions remain while a variable exists. Disable rejects future
consumption by new and retained runs but cannot recall already delivered values.
Provider revocation is external. Deletion blocks draft and retained published
references, active captures, and running comparisons. Allowed deletion removes
current protected revisions; safe history survives and backups may retain
ciphertext. Later retries requiring a deleted revision fail explicitly.

Portable format 4 includes safe variable requirements across all exported
definitions and retains format-3 cleanup identities and prompt support. It excludes
all values, keys, local key paths, and historical captures. Imports require explicit
same-kind local binding or unset provisioning. Bindings remain outside published
definitions; conflicting existing bindings reject atomically. Earlier formats
remain supported for variable-free workflows. Variable-bearing legacy imports must
be re-exported as format-4 bundles.

Model aliases map logical roles (e.g. `builder`, `reviewer`, `evaluator`) to an ordered candidate list of `{ model, effort?, profileId? }`. Workflows and Agent nodes reference an alias anywhere a model ID is accepted (`agentModel` and `model`).

## Timers

Duration and timestamp Wait nodes persist `resumeAt` on their execution and stay waiting until that deadline. The runtime resolves the deadline once from a duration or an ISO timestamp at an input path. Wait returns its input unchanged and enforces its output contract. Cancellation prevents continuation; restart retains the deadline. The server checks timers on its one-second engine tick and at operations that advance the engine. An overdue timer resumes on the next check, including after downtime.

A polling Wait (`timing.kind: "poll"`) keeps `nextCheckAt` (mirrored to `resumeAt`), an optional `timeoutAt`, and the latest `check` result on its execution. When a check is due, the pump runs it as a local job like a Script or Fetch step while the execution stays `waiting`; a matching result finishes the step with the check output merged into an object input, while a mismatch or failed check schedules the next check. A successful check whose output lacks the path or whose matched completion violates the output contract fails the step. Fetch binding failures are recorded and retried like request failures. The deadline aborts an in-flight check and follows the `timeout` route with the original input, bypassing the Wait output contract. Settlement rechecks the deadline before accepting a result, so late results cannot override Timeout. Cancellation aborts a check in flight; a restart re-runs an overdue check unless declared resources retain uncertain ownership. Reconcile that exact execution attempt before a resource-protected check can repeat.

Agent nodes optionally specify `unclaimedTimeoutMs`. Available work carries a persisted `availableUntil`. Claiming clears that deadline. Releasing a failed or expired claim starts a fresh deadline when another attempt is allowed. At expiry, the runtime marks available work `timed_out`, records a `work.timed_out` event, and finishes the node through `timeout` with its original input. The Agent result contract applies only to `default`; the destination validates timeout input. Publication requires both routes when the deadline is enabled. Executions record their outgoing `port` for inspection. Existing definitions and records without these optional fields retain their behavior.

Timers create no sleeping processes and consume no steps while waiting. They work inside Batch item paths and referenced workflows with ordinary cancellation and collection. See [timer configuration](timers.md) for JSON examples and limits.

## Continue-as-new chains

Continuing Exits are terminal checkpoints in standalone runs. Core defines the optional Exit configuration, common finite maxRuns and lineage contracts; runtime owns chain creation and cancellation. Storage persists optional run links and additive runChains records. A nested savepoint commits predecessor completion, checkpoint execution output, successor allocation, reciprocal links and the latest pointer together. Invalid input or failed persistence leaves no successor. A continuing Exit validates the workflow input contract instead of final output; only normal Exits produce run output.

Successors inherit the predecessor's current version, version policy, and prompt capture but reset run-local input and continuity scope. Pinned chains retain their original version by default; compatible moves cannot alter the chain configuration or cap. The chain relationship does not consume child ancestry depth. Budget scopes include all members before following ordinary/detached descendants. Existing per-run cancellation remains unchanged; explicit chain cancellation stops the latest member and prevents retry or rollover, preserving detached lifecycles. Comparisons, simulation and nested Workflow invocation reject continuing definitions.

The engine yields after one rollover per chain per pump and reads only active run documents for execution. This avoids deserializing completed execution histories every tick, while SQLite scans and retained usage/budget aggregation still grow with archive size. See [continue as new](continue-as-new.md) for bounds and operations.

The query still computes placement and totals across the requested workflow scope. Board settings check column references in drafts, retained versions, and retained events.

Human input uses the External input wait with a per-visit capture of the question, context, evidence, and answer contract. The shared response transaction checks the visit and revision, validates the answer, and records the receipt. It accepts the answer in that transaction when no pause or hold applies. A held answer requires a separate acceptance after release. Only the request targeted by the answer resolves.

## Scripts and interruptions

Scripts run in JavaScript or Bash child processes. New nodes default to JavaScript; definitions without a `language` field retain Bash behavior.

JavaScript receives `input` and must return a JSON value. The runner wraps the code in an async function, supports top-level `await`, `require`, and dynamic imports, and reports errors against `script.js` with editor line numbers. `console.log`, `console.info`, and `console.debug` are redirected to stderr so they do not corrupt the JSON result. Bash reads JSON on stdin and must emit one JSON value on stdout.

Both languages run with your OS permissions. Script execution is not sandboxed. A Script node or polling Script check's `environmentMode` selects which server environment variables it receives. Omitted or `"inherit"` passes the whole service environment, as before modes existed, so saved workflows and imported bundles keep their behavior. `"minimal"` passes only `PATH`, `HOME`, locale variables (`LANG`, `LANGUAGE`, `LC_*`), `INTERLOCK_*`, bound saved variables, execution context and names listed in `environmentPassthrough`. Scripts and polling checks added in the editor start in minimal mode; the inspector's **Server environment** control switches modes. When a minimal Script fails and its source or error output mentions a withheld server variable, the error names it and the fix. Installed copies default to the directory where `interlock` starts; development defaults to the checkout. `--workdir` on the installed CLI or `INTERLOCK_WORKDIR` overrides the working directory. Workflows, Script nodes, and polling Script checks can also bind `cwd` dynamically from run data (using value bindings such as `$input.path` or `$steps.<id>.output.path`). Node-level `cwd` overrides workflow-level `cwd`. Bound directories must resolve to existing directories contained within configured `allowedRoots` (via `--allowed-roots`, `INTERLOCK_ALLOWED_ROOTS`, or server execution settings). Symlinks are followed to their canonical targets and validated against `allowedRoots`. Any path escape or missing directory immediately fails the Script step or check without falling back to defaults. The resolved directory is recorded on the execution record as `resolvedCwd`.

A Script node's `timeoutMs` defaults to 60,000 milliseconds and accepts integers from 100 to 3,600,000. Scripts also have output limits. Omitted `executionMode` or `"foreground"` retains the server-owned runner. Cancellation kills its process group, shutdown stops it, and restart marks an interrupted execution failed. Interlock never automatically replays interrupted operations. An explicit retry can repeat effects.

Opt into `executionMode: "background"` or the editor's **Background execution** switch for a local supervisor that survives server shutdown. This requires a file-backed database on the same host and user account. The server persists launch intent before spawning; the supervisor owns the Script process group, absolute deadline and encrypted progress/result receipts beside the database in `<database>.scripts/`. Command, input, environment and per-execution encryption key travel through stdin. The existing protected-value vault stores the key. Keep the database, spool and original vault key together for recovery. Workflow exports exclude these local execution records.

Restart reconnects to the same run and execution. OS PID, process start identity and an unpredictable execution token identify a live supervisor. Authenticated terminal receipts can be recovered after the supervisor exits. The existing guarded settlement transaction validates the JSON result, applies optional failure routing and advances once. No missing launch or result record authorizes a replay. Missing, corrupt or mismatched evidence marks the execution `uncertain` and fails terminally. After inspecting the original process group and external effects, an operator must confirm `stopped:true` with a reason through `runs.script`, CLI `interlock script`, or MCP `manage_script` before explicit retry can create a new execution. This guard also covers failed attached descendants resumed by a Workflow or Batch parent retry. Completed children are retained, and detached runs keep their independent lifecycle.

Cancellation writes a durable stop request to the verified supervisor, which kills its Script process group. A stop during the launch handshake is recorded for the original supervisor before it starts the Script. `stop` also cancels the owning run. Use `inspect` afterward to confirm cleanup; an unverifiable supervisor requires explicit stopped reconciliation. Server shutdown only disconnects background monitoring. Deadlines remain enforced offline. Polling Script checks keep their existing server-owned behavior.

Run inspection includes `execution.background` with state, deadline, supervisor PID/start identity and at most 8 KiB of recent stderr progress. JavaScript console logs use stderr; stdout remains one JSON value with a 1 MiB limit. Secret-consuming Scripts suppress live stderr until completion, then apply the existing complete-buffer redaction before tail selection. Their buffered stderr is bounded to 1 MiB and encrypted on disk. Non-secret progress retains a bounded tail. Success data is redacted before validation and persistence, as with foreground Scripts. Owner-only spool files, their protected encryption keys and launch records are retained separately from run history; deleting run history does not remove them. Spool retention is not automatic. History deletion blocks unfinished or uncertain background executions until outcome inspection or explicit stopped reconciliation.

This mode does not survive host loss, guarantee transactional external effects, or manage detached processes that leave the Script's process group. If a supervisor disappears without a valid result, inspect effects and recover explicitly.

Script execution happens outside database transactions. Agent claims and result submission remain available while scripts run. Completed script results are committed before advancing dependent steps.

Script nodes and Script checks in polling Waits receive these environment
variables. They are delivered in minimal environment mode too. Workspace hooks
do not receive `INTERLOCK_URL` or `INTERLOCK_API_TOKEN`. Read them through `process.env` in JavaScript or shell variables
in Bash. JavaScript's `input` and Bash's JSON stdin keep their usual format.

| Variable                              | Value                                                                                                                                                                                                         |
| ------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `INTERLOCK_RUN_ID`                    | Run executing the script. Use this ID to inspect the run.                                                                                                                                                     |
| `INTERLOCK_ROOT_RUN_ID`               | Outermost ancestor run. A top-level run identifies itself. A detached child keeps its original ancestry.                                                                                                      |

outside that prefix for saved variable bindings to avoid collisions. Explicit
saved bindings take precedence over execution context, which takes precedence
over matching values from the service environment. The context
values are strings and carry execution identity only.

A workflow or node ID is omitted if it contains a NUL byte, cannot be
represented as UTF-8, or exceeds 16 KiB in UTF-8. Existing definitions with
these IDs can still execute.

For foreground Scripts, if adding context exceeds the OS process launch limit,
Interlock uses the original environment. This fallback applies only before the
Script starts. The background supervisor records Script child-launch errors as
operation failures; a missing supervisor leaves an uncertain outcome.

A retry of a retained execution without an attempt record treats that
execution as attempt 1.

## Local interfaces

The main service binds to `127.0.0.1` and rejects unexpected request hosts and browser origins. It is a single-user local service. A per-install [API token](connect-harness.md#api-token) is sent by first-party clients; on loopback it is required on `/api`, `/trpc`, `/mcp` and `/events` only when `INTERLOCK_REQUIRE_TOKEN` is set, so by default local processes can invoke its interfaces. `startServer` always requires it, and refuses to start without one, when given a non-loopback `hostname`; no user-facing option sets one yet. The check lives in `packages/server/src/apiToken.ts`. It must not be exposed through a public tunnel.

Installed copies use `~/.interlock/interlock.db`; development uses `.interlock/interlock.db` inside the checkout. `interlock` starts the engine and built UI in the foreground. Its `--port`, `--db`, and `--workdir` flags override defaults. Development uses `pnpm dev` for the engine and Vite UI, or `pnpm start` for the engine and previously built UI.

The Hono listener exposes Streamable HTTP MCP at `/mcp`, behind the same host, origin, and 2 MiB request-body restrictions as the other APIs. Each POST creates an MCP server and SDK transport, calls the shared server router, returns JSON, and closes the transport. There are no transport sessions or server-initiated notifications; GET and DELETE return 405. Runs and claims remain in SQLite across requests and restarts. The endpoint URL stays stable across upgrades at the same address, for both global and npx startup.

The shared client sends `workflows.validate`, `work.preflight`, and `work.size` as individual POST queries to avoid request-line limits on candidate definitions, results, and preview samples. The server accepts POST for these queries while retaining legacy GET and batched GET validation. The operation remains read-only. Requests above the body limit receive HTTP 413 with the limit and a request-size correction message.

The plain [HTTP API](http-api.md) at `/api` (`packages/server/src/httpApi.ts`) serves scripts and other ordinary HTTP clients behind the same host, origin, token and body-size checks. Its routes call the shared router procedures (`workflows.catalog`, `runs.startSummary`, `runs.briefing`, `runs.result`, `runs.cancel`, `testbench.evaluationPlan`, `testbench.recordEvaluation`) and only map request and response shapes and HTTP statuses. Start conflicts are `RunStartConflict`, an `InterlockError` subclass, so `/api` can answer 409 while tRPC and MCP keep their existing errors.

`interlock mcp` remains a stdio bridge to an already running engine. The connection dialog defaults to HTTP and provides a stdio fallback: checkout paths in development, the portable CLI command for installed copies, and optional absolute paths derived from the installed runtime.

The UI uses tRPC requests and server-sent notifications, with periodic refresh as a reconnect fallback. Events and node execution data remain in SQLite. `INTERLOCK_DB` changes the database location. `INTERLOCK_URL` changes the service URL used by CLI and MCP callers.

Workflow recovery includes child run/version/execution references and routes failed child outcomes or rejected successful output. Caller input/dispatch errors, cancellation and persistence failures stay terminal. Allocation and caller links commit together for route-enabled calls, and recovery writes use a savepoint. A handled child cannot be retried independently; retrying a failed recovery step does not replay the child. A restarted caller may handle an interrupted child's retained failed outcome without replaying the operation. Existing success contracts apply only to the default route. See [failure routes](failure-routes.md).

Core defines Fetch configuration, validates bindings at publication, and resolves requests through the same pure function used by the UI preview. Runtime sends requests outside storage transactions with an abort controller shared with run cancellation. Resolved requests persist on node executions. HTTP errors retain their response output; explicit retries create a new execution. Pending requests fail on restart because remote side effects are uncertain. Resource-protected requests also retain uncertain ownership when dispatch begins but a complete response is not observed. Ordinary Fetch fails terminally on this uncertainty; polling Fetch waits for exact remote-stop reconciliation before another check, with its remaining deadline suspended. Failures before dispatch and fully observed HTTP or JSON errors release resources normally. See [Fetch requests](fetch.md) for the configuration and response contract.

## Managed Agent execution

`runtime/executors/manager.ts` owns dispatch inside the server process, using Store change notifications and a one-second recovery check. Core owns portable references and local profile contracts. Profiles, native session mappings and execution provenance use separate local document collections; workflow bundles carry references only. Adapters own native transports and never own Interlock claims. Claude Code uses the official Agent SDK core with an explicit installed executable; Codex uses app-server JSON-RPC over stdio; Pi uses its JSONL RPC protocol and an explicit temporary permission extension. Pi waits for `agent_settled` before accepting a JSON result envelope. Its response usage is aggregated per assignment, while other adapters report native session counters. Custom harness profiles (`harness: "custom"`) support direct turn subprocess/HTTP execution with schema validation and result envelope unwrapping, or delegated launcher mode where Interlock executes a launch command or HTTP POST endpoint with a one-time `claimTicket`. The external session must present this ticket to `claim_work` to acquire the assignment; launcher mode optionally polls `status`, delivers policy-controlled idle `message` nudges, halts sessions via `stop`, and triggers session `archive` when the final assignment in the run completes.

The manager uses ordinary claim, renew, usage, submit and failure paths. One revision-checked local setting limits managed assignments across all profiles and workflows, default 3, with positive whole-number limits or explicit null for Unlimited. Settings changes affect new starts without interrupting active work; optional current profile concurrency also gates new dispatch without interrupting active work. Pending delegated launches consume both caps, and a saturated profile does not block another profile. Workflows and Agent nodes can bind `cwd` dynamically from run data with containment validated against `allowedRoots` configured on the executor profile or server settings. An invalid directory or path escape leaves the assignment unclaimed with a `cwd_blocked` blocker reason. For continuity groups, the resolved working directory is pinned upon initial session launch so subsequent assignments cannot shift the working directory. Direct Agent selections use the node override, applicable concrete workflow defaults, then harness defaults. Null effort uses native defaults. See [Agent presets](managed-executors.md#model-aliases) for legacy alias routing and preset permissions. Assignments capture these overrides and their sources as `executorModel`/`executorEffort` and corresponding source fields. Model-specific effort support is checked before a new managed claim. Native model/effort discovery is on demand, cached and bounded, through the shared executor API; it starts no Agent turn. Published workflow `agentPermissions` optionally overrides each selected harness default; the assignment captures it as `executorPermissions`. The manager records the effective permission mode and source, captures the profile at first claim and retains that snapshot for retries and a continuity group. Ungrouped and fresh work start independent native sessions; grouped work binds a manager-owned logical session to its native session. Profile edits affect later unbound assignments. Disabling a profile stops its running assignments. Uncertain interruption holds work and preserves resource ownership until explicit reconciliation; startup never blindly replays a previously active process. Detached lifetimes retain their existing semantics. See [managed execution](managed-executors.md).

Recognized model refusals before task actions use ordinary work holds with managed state `needs_model`. Adapters classify native errors and confirm process cleanup; the manager owns holds, resource release, and explicit `retry_model` recovery. Holds consume no Agent failure allowance or shared execution slot. Recovery persists a replacement without changing historical attempt profiles or published assignments, resets effort to native defaults, and resumes through normal claim admission. Continuity sessions retain their native identity and original requested intent while recording recovery model/effort sources. These holds survive restart without requiring uncertain-process reconciliation. Other failures retain their existing handling.

Managed session recovery policies configure automated retry and continuation across three precedence tiers (Agent node override > Workflow definition > Profile default). Adapters classify errors into permanent (rejected immediately without retry), transient (eligible for exponential backoff retries within a rolling window), and missing result errors. Missing results dispatch continuation prompts in the same session before failing the attempt (`continueOnMissingResult`). Transient errors back off exponentially (`initialBackoffMs * 2^retryCount`); delays freeze while a run is paused, and pause holds are excluded from rolling window calculations. Exhausting transient retries escalates work to a `Needs attention` hold (`category: "other"`) with diagnostics rather than failing or looping indefinitely. Recovery events are recorded on the execution attempt and surfaced in inspection.

## System diagnostics and health check (`doctor`)

Interlock provides a unified read-only readiness and health check via `interlock doctor [--live] [--json]`, the MCP tool `doctor`, the shared server API `system.doctor`, and the UI Diagnostics page at `/settings/diagnostics`.

Core owns the diagnostic schemas (`diagnosticCategorySchema`, `diagnosticStatusSchema`, `diagnosticCheckSchema`, `doctorReportSchema`, and `doctorOptionsSchema`). Diagnostics evaluate five categories without mutating state or starting workflow runs:

1. **System**: Checks engine version match, SQLite database integrity (`PRAGMA quick_check`), schema migration version, database file size and run history count, and available disk space (`statfsSync`). It also warns about each disabled variable, naming the workflow drafts and retained versions that reference it, because upgrading to 0.3.0 deletes disabled variables; with none disabled it reports that the upgrade needs no manual variable step.
2. **Harnesses**: Verifies enabled harness profiles, binary detection, version discovery, `cwd` and `allowedRoots` existence, and optional live single-turn auth/model verification (`--live`).
3. **Triggers**: Checks schedule execution lag (>60s), consecutive failures and automatic pauses across enabled schedule and lifecycle event triggers.
4. **Blockers**: Inspects active library and workflow pause holds (`pauseHolds`), uncertain resource and executor holds (`uncertainClaims`, `uncertainOperations`, and uncertain `workResources` reservations), active stalled work items (`currentStalls`), and `needs_model` execution holds (`managedExecutions`).
5. **Workflows**: Validates missing, disabled, unset, or locked variables, known missing aliases and unavailable candidate profiles, and required saved prompt content or exact publish pins in latest published workflows. Literal native model IDs remain valid. Released pauses do not count as active blockers. Detects unpublished content edits only in non-archived workflows, ignoring direct node positions; archived workflows retain their published-dependency checks.

The overall status evaluates to `ok` if all checks pass, `warn` if warnings exist without errors, and `fail` if any check fails. The CLI exits with code 0 on `ok` and `warn`, and code 1 on `fail`.

### Lifecycle event dispatch and quiescence

Runtime captures compact lifecycle context with the source transition and creates durable event/trigger receipts in the same transaction. Event triggers observe completed, failed, cancelled, needs_attention and stalled transitions, with library or workflow scope and optional owned children. A completed Exit filter narrows completion delivery. Handler startup uses ordinary RunStarts and admission, the latest published target, and the shared pause/failure gates. See [event contracts](events.md).

Event triggers start a workflow, passing the compact lifecycle event as its input. A handler can use Fetch nodes for outbound HTTP requests.

Each handler run persists a causal `triggerChain`, inherited by child, detached and continued runs. A chain cannot repeat a trigger, and configurable `maxTriggerDepth` defaults to 2 with a 1–20 bound. Suppressed transitions remain inspectable. Delivery history retains at most 200 settled rows plus pending work. Pair receipts survive log trimming, so restart and repeated events cannot repeat the effect. Pending compact context stays internal to dispatch; ordinary inspection returns bounded metadata.

Terminal triggers can set `waitForQuiescence: true`. Runtime checks the entire source tree, including detached and continued runs, Scripts, managed executions, active claims, uncertain resource ownership, revoked Agent attempts, interrupted Fetch operations and foreground Scripts interrupted by restart, even without named resources. Expiry or cancellation does not prove stop. Existing explicit stop/reconciliation operations release uncertainty before dispatch. Briefings expose bounded blockers. This gate does not change ordinary cancellation boundaries or stop external processes.

Shared trigger CRUD and inspection serve UI, CLI and both MCP transports. Portable format 8 exports safe event configuration with source workflow dependencies. Imports disable included triggers, omit operational history and receipts, and reset local event delivery state. Existing schedule history remains.
