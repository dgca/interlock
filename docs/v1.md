# Current limits

The bounds of what Interlock implements and what it does not support yet. See the [feature index](features.md) for implemented features by area.

## Security and access

Interlock is a single-user local tool. The server listens only on `127.0.0.1`; there is no configurable listen address, user account or per-user permission. The [API token](connect-harness.md#api-token) is optional on loopback unless `INTERLOCK_REQUIRE_TOKEN=1` is set. Scripts and custom harness commands run with your user account's access and are not sandboxed. The `minimal` [server environment](architecture.md#scripts-and-interruptions) limits which server variables they receive, not what they can read or run. Script approval covers imported content, and agent-authored content only when the library setting extends it. The Fetch private-network check resolves the host once before the request and does not protect against DNS rebinding; polling Fetch checks are not checked.

Automatic self-improvement, model-driven evaluation, automatic promotion, direct provider adapters, sandboxed script execution and multi-user access remain future work.

## Agents and executors

Agent execution supports connected harnesses, manual submission and opt-in managed Claude Code, Codex, Pi, and custom harness sessions. Managed dispatch requires an enabled local profile and installed, authenticated native executable or configured custom command/endpoint. Direct model-provider API execution, OpenCode dispatch, Channels and managed local Git trial containment are deferred. HTTP client configuration is provided for Codex, Claude Code, and OpenCode, plus generic Streamable HTTP instructions. Claude Desktop configuration uses the retained stdio fallback. HTTP MCP has no transport sessions or standalone SSE notification stream. Automated tests verify the MCP transport and packed installation; they do not establish compatibility with every client version or approval policy.

Managed Agents support node model/effort overrides above workflow and harness defaults. Effort choices use native model capability discovery; unsupported explicit choices remain unclaimed. Connected Agent model tiers remain advisory. Harness settings do not manage tool or skill installation; exact-name capability declarations remain available through advanced API/MCP configuration. Automated recovery policies (`continueOnMissingResult` up to 10 turns for missing structured envelopes and `transientRetry` up to 10 retries with exponential backoff and pause-aware rolling window accounting) operate at node, workflow, and profile levels, escalating exhausted transient retries to Needs attention holds.

Agent nodes support optional [run-local continuity groups](context-continuity.md), declared session identities, and auditable replacement handoffs. Interlock enforces identity declarations; the harness owns actual session continuity and fresh isolation.

Tool and skill requirements are names checked against executor declarations. The executor supplies their implementations. Interlock does not load arbitrary skill files or manage outgoing MCP connections itself.

Managed [session transcripts](managed-executors.md#transcripts-and-operator-messages) capture new native executions with 32 KiB entry, 2,000-entry and 10 MiB execution limits, a 256 MiB library budget including reserved receipts, and automatic expiry 14 days after execution ends. SQLite/index overhead, backups, and native harness logs are separate. Oldest ended content is evicted before active content. Custom harness capture is partial; historical conversations are not backfilled. Supported active native sessions and custom launcher message hooks accept bounded operator guidance with durable request receipts. Unknown delivery never automatically resends. Binary content and private reasoning are excluded.

[Agent result preflight](result-preflight.md) checks captured output contracts and current claims without mutation. Submission exposes structured correction diagnostics. Optional Agent resultRules check required output paths and equality with captured input paths before acceptance. Arbitrary validators remain outside this feature.

[Assignment size diagnostics](assignment-size.md) measure captured assignments and sample-based Agent previews. They report bytes and advisory warnings, not token or billing estimates, and never change delivered context.

## Workflows and graphs

Input and output contracts have a field editor with named fields, display labels, required flags, descriptions, nested objects and lists, and text choices. Pasting example JSON generates a draft contract and highlights assumptions to review. Advanced JSON Schema remains available; schemas outside the visual editor’s supported subset stay intact in advanced mode. The run dialog provides fields for common object schemas and JSON editing for complex values. Read-only preflight checks a conservative primitive, object, array, and binding-path subset. Ambiguous sources and unsupported schemas report unknown. There is no static proof that every connected node's contracts are compatible. Actual inputs and outputs are checked at execution time.

The node editor suggests an input shape from connected output contracts and input bindings when no explicit node input contract exists. It offers paths and match-value types where that shape is known. The author can copy the hint into the input contract to enforce it. Ambiguous or unknown upstream shapes remain unrestricted; inference does not establish static compatibility.

Batches default to 200 items per execution. Their `maxItems` setting accepts 1 through 10,000 independently of the 50 concurrent item limit and the 10 nested workflow levels shared with Workflow nodes. Larger lists fail before dispatch. Large batches increase local resource use and stored history; 10,000 is a validation bound, not a throughput guarantee. Each item path stays inside an explicit Batch group on the main canvas. Every item branch must connect to its group's End handle. Output emits the ordered results only after collection finishes. Workflow-level back-edges are allowed: a route can target an upstream node other than Entry, and the same run executes that node again. Each visit counts toward `maxSteps`. Batch item paths must be acyclic and reach End. [Parallel groups](parallel.md) run 2–50 distinct named, acyclic branches and join all results. They share their parent step limit and cannot nest inline with Batch or another Parallel group. Arbitrary graph joins and partial-result joins are unsupported.

Detached Workflow nodes return run references immediately. Their work survives ordinary parent cancellation and remains visible in Runs. Batch concurrency limits dispatching items, not the lifetime of detached runs. Explicit tree cancellation can include detached descendants. Parallel joins collect the immediate run reference of a detached call. There is no detached completion join, callback, or global detached-work concurrency limit. See [Workflow execution](workflow-execution.md).

Fetch nodes support HTTP/HTTPS requests, typed input bindings, JSON bodies, response inspection, and explicit retry. Responses are limited to 5 MiB and requests to 120 seconds. Streaming outputs, binary downloads, OAuth configuration, and multipart forms are outside the current scope.

Wait durations and unclaimed Agent timeouts support up to 365 days. Timestamp waits require an ISO timestamp with a timezone. Timers advance on engine checks, normally once per second, and resume overdue deadlines after restart. Claimed assignments have renewable leases and optional active per-attempt `maxExecutionMs` deadlines.

Saved prompts provide centrally maintained Markdown guidance. Each workflow invocation captures current instructions at startup. Batch items and Parallel branches inherit that capture. Workflows can opt into exact prompt revision pinning at publish time (`pinPromptsAtPublish`). Per-node prompt pinning, prompt variables, attachments, archive, revision-restoration UI, and external skill import are outside the current scope.

Child ownership has one level. Only the owning workflow can reference its children. MCP and the shared API support adoption, reparenting and release of existing workflows while preserving identity and history. Foreign drafts and retained published references block adoption or reparenting; obsolete caller versions require explicit cleanup. Ownership move UI, main-library child search, and parent clone/deletion with children are not implemented. Parent clone is disabled when children exist, and parent deletion reports a blocking error. Portable export includes children and dependencies. Existing workflows are not automatically reorganized.

The retired ownership proposal leaves several design constraints for future work, not a committed roadmap. Parent cloning would need fresh child IDs and remapped draft/version pins while preserving shared library references. The copy would include each child's current draft and required published versions, preserving version numbers. The parent would start unpublished, and no runs would be copied. Parent deletion would need one guarded transaction over the parent and its children, with external references and active runs blocking removal. A copy-as-child action would create an unpublished copy and revision-check the selected caller draft. Library-wide child search would need an explicit scope and owner breadcrumbs. These operations remain unimplemented.

## Runs and data

Run continuation returns bounded current snapshots, not event deltas or historical payload replay. Each list defaults to 20 records and caps at 100 with exact totals. Targeted values default to 64 KiB and cap at 256 KiB. Large scoped histories still require metadata aggregation; list bounds do not bound arbitrary stored text. Server restart resets cursors explicitly.

Background Script recovery requires the same local host/user, a file-backed database, its adjacent encrypted spool and original protected-value key. Foreground Scripts and polling checks retain interruption behavior. Host loss, process-group escape and automatic spool retention are outside this mode.

Results are JSON stored in SQLite. The UI exports run records and workflow definitions. The editor compares its draft with the latest published version before publication; comparisons between arbitrary historical versions are not implemented. Managed Git comparisons retain bounded patch/untracked-file exports locally. General artifact storage, rendered recommendation documents, and replay against captured sources are not implemented.

Resource coordination covers cooperating Agent claims and declared Script, Fetch, and polling Wait operations. Polling reservations last for each check, with resource queue time excluded from probe and Wait timeouts. Resource-protected Fetch transport failures retain uncertain ownership until remote work is confirmed stopped; polling checks do not repeat during reconciliation. Unmanaged writers, undeclared operations, and other libraries remain outside coordination; there is no fencing or FIFO guarantee.

Tags filter run queries, Runs views, and performance reports by every exact key/value pair before sampling. Performance reports aggregate only selected runs, without a separate tag grouping. Per-run usage inspection and workflow comparison reports retain their existing scopes.

## Usage and reports

Usage reporting depends on executor-supplied or observer-supplied telemetry. Observer reports require retained ended attempts (or active/recently completed runs for run-level observer streams) and take precedence over executor snapshots in totals and budgets. Provider account access, automatic pricing, and billing reconciliation are not implemented. Reported-usage budgets can overshoot; claim-count limits bound new reservations. Existing attempts without receipts retain unknown usage; completed work is not assumed to have complete reporting.

Workflow performance and cost reports select the newest matching runs by creation time, with an optional inclusive `since`/`until` window and a sample limit of 500 by default, up to 5000. Omitted dates impose no date restriction. Supplied bounds must normalize after fractional rounding to a UTC instant within years 0000 through 9999; invalid dates, offsets and out-of-range bounds reject with validation errors. The UI initially requests the past seven days and up to 1000 runs. Time percentiles interpolate between sorted observations at `(count - 1) * percentile`, rounded to two decimals. Human wait sums Input node executions and recorded work holds, without library/workflow pause intervals. Attempt coverage records the presence of a selected model snapshot, not completeness of individual token or cost fields. See [report metrics and limits](usage-reporting.md#metrics-and-limits).

## Testing

The testbench supports live comparisons of two published versions with root-scope output and route assertions. Exact per-side prompt manifests and requested model/profile/environment metadata are supported; external executors choose how to honor requests. Optional [local Git trials](local-git-trials.md) prepare independent checkouts and track evidence/cleanup for trusted local work. They do not contain arbitrary code or verify external tool restrictions. Comparison sample budgets require tree scope and are independent allowances, not pooled experiment or billing caps. The improvement starter never edits production or shared prompts and cannot establish general improvement from repeated tuning on the same cases. Nested checkpoint selectors, replay and a comparison dashboard remain outside this increment.

Fixture simulation supports published Entry/Exit/Agent/Script/Fetch/Condition/Switch, Wait (duration and polling), Human input, Batch, Parallel, and child Workflow graphs through MCP, shared API and CLI. Saved ordered fixtures substitute Agent results, Script/Fetch operations, and waited child workflows, and can exercise Agent unclaimed timeouts (`timedOut: true`). Wait and polling checks advance on a deterministic virtual clock. Reports include route coverage and untested edges. Batch items and Parallel branches run one at a time, and their steps take each node's fixtures in item and branch order. Continue-as-new Exits are rejected before execution. Reports prove only simulated control flow and contracts. See [bounds and lifecycle](workflow-simulation.md).

## Automations

Schedule triggers support intervals of at least 30 seconds and five-field cron with IANA zones, JSON templates and metadata bindings. Overlap skip/queue/allow and missed skip/run_once are persisted with idempotent slot starts. Optional failure pauses and excessive lag appear independently in Needs attention. Format 5 transfers schedules disabled. See [schedule limits and policies](schedules.md).

[Lifecycle event triggers](events.md) react to completed, failed, cancelled, needs_attention and stalled transitions. Triggers start workflow handlers, which can use Fetch nodes for outbound HTTP requests. Source scope covers one workflow, its owned children, or the library, with an optional completed Exit filter. Terminal events can wait for full-tree quiescence, including detached descendants, Scripts and uncertain claims. Durable event/trigger receipts and inherited trigger chains prevent repeated effects. The configurable depth cap defaults to 2 and accepts 1 through 20. Pending events honor target pauses and ordinary admission; failed starts and handler runs participate in automatic failure pause. UI, CLI and MCP expose bounded delivery history and suppressed outcomes. Format 8 transfers event configurations disabled.

Custom launchers can opt into capped idle messages followed by confirmed stop/relaunch through ordinary attempt and claim budgets. Native/direct adapters retain observational stalled attention. Managed execution deadline revocation, uncertain stops and restart require reconciliation; automatic session restoration is not guaranteed. See [timers](timers.md#stall-detection-and-active-attempt-deadlines) and [idle launcher recovery](managed-executors.md#recover-an-idle-launcher).

## Diagnostics

Doctor is a read-only diagnostic and readiness check; it does not repair databases, auto-pause or resume schedules, release holds, or modify workflow definitions. Free disk space is evaluated using the local filesystem (`statfsSync`) of the store path; remote storage volumes or container mounts with abnormal statfs semantics may report 0 or fallback values. Live harness verification (`--live`) performs a bounded single-turn request against enabled harnesses; network timeouts or provider throttling will be reported as warning or failure checks without side effects on running workflows.
