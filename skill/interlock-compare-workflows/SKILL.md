# Compare Interlock workflows

## Choose the evidence

- If the user gives a comparison ID, read its captured selection and report first. Resume that comparison if asked to continue it. Reviewing an existing report needs no new runs.
- To check contracts and routes with supplied outcomes, use `workflow_simulation` on each published version with equivalent saved fixtures. It substitutes every Agent, Script, and Fetch outcome. It supports flat graphs and rejects Workflow, Batch, Wait, External input, and Agent unclaimed timeouts. Use the result as simulated control-flow evidence. [Fixture simulation](https://github.com/dgca/interlock/blob/main/docs/workflow-simulation.md)
- To measure real behavior, use a paired live comparison. Scripts, Fetch requests, and agents can perform external actions. Inspect both versions and their children for effects before starting. If a comparison needs test isolation, keep its records in a separate library and direct all external actions to authorized test services with scoped credentials. For local Git work, follow the trial policy and verify the executor's workspace and outbound-write restrictions before claiming. [Local Git trials](https://github.com/dgca/interlock/blob/main/docs/local-git-trials.md)

## Plan the comparison

1. Define the change under test, required behavior, and evidence that would justify adoption. Use exact published version numbers of the suite's workflow. If a draft needs publishing for testing, use an authorized test copy with its dependencies and ownership intact. For a large version history, select the relevant definitions locally from a CLI export. [Portable bundles](https://github.com/dgca/interlock/blob/main/docs/agent-workflows.md#export-and-import-portable-bundles)
2. Pick cases before inspecting candidate results. Cover typical inputs, cases the change should improve, and failures or fallbacks that must stay intact. Reuse a suitable suite with `read_test_suites` or save one with `save_test_suite`. Use explicit inputs or original inputs from source runs of the same workflow. Use stable case IDs and checks that make sense on both versions. Node and route checks must target the root graph. If a fold moves a route to another node, use a common downstream assertion or verify the version-specific routes separately. [Saved cases and assertions](https://github.com/dgca/interlock/blob/main/docs/workflow-testbench.md#save-representative-cases)
3. Hold unrelated settings steady. To isolate a saved prompt change, keep the same workflow version on both sides. Select complete per-side `promptRevisions` manifests, including child prompts. Each side without a manifest captures current saved prompt content. A published version alone cannot recover the historical prompt library. Executor and environment requests describe intended conditions. Arrange the actual executors separately and check declared and reported attribution after execution. [Exact side configurations](https://github.com/dgca/interlock/blob/main/docs/workflow-testbench.md#select-exact-side-configurations)
4. Call `preview_workflow_comparison` with the suite ID and revision, exact baseline and candidate versions, and chosen repetitions, concurrency, configurations, and budget. Check `canStart`, blockers, captured pins and configuration differences, and `rootRunCount`. Child runs add work. For bounded Agent work, use a tree-scoped `sampleBudget` on each root. Account separately for evaluator work. Each sample gets its own allowance. Budget for the full set of samples and use separate controls for provider spending and Script or Fetch effects. [Preview and budgets](https://github.com/dgca/interlock/blob/main/docs/workflow-testbench.md#preview-and-start-a-comparison)

## Run and inspect

1. When live execution is authorized, `canStart` is true, and the preview matches the plan, call `start_workflow_comparison` with the same selection, its `confirmation`, and a caller-generated `requestId`. Record the arguments, request ID, and returned comparison ID. After an uncertain response, retry the identical request. If the selection changes, preview it again and use a new request ID for the new comparison.
2. Follow `read_workflow_comparisons` with `request.action: "report"` and the comparison ID. The engine handles work configured for managed execution. For connected execution, scope discovery to the comparison's sample roots and follow the ordinary claim, renewal, preflight, and submission rules. Use run briefings to distinguish blockers from completion. Account for detached descendants even after a root finishes. If cancellation is authorized, use the comparison's cancel action and check for independent descendants afterward. [Run and resume assignments](https://github.com/dgca/interlock/blob/main/docs/connect-harness.md#complete-a-run)
3. Compare matching case IDs and repetitions. Follow the report's returned offsets and use `get_run_result` for selected outputs. If you need the original inputs or assertions, read the captured case through the comparison's `case` action. Report execution outcomes, structural checks, quality, elapsed time, and reported usage separately. For each delta, match the case and repetition. Compare the same elapsed measure on both sides. Compare cost only when both samples have complete usage costs in the same currency. Candidate minus baseline is the delta direction. Unknown or mismatched evidence stays explicit. Later retries do not replace original observations. [Reports and measurements](https://github.com/dgca/interlock/blob/main/docs/workflow-testbench.md#compare-measurements)
4. If the decision requires semantic quality evidence, read the [artifact evaluation procedure](references/evaluate-artifacts.md). Starting an evaluator is a separate live run that requires authorization. Report the comparison ID, captured selections, paired results, and remaining gaps. Recommend adoption, retaining the baseline, or gathering specific missing evidence based on the original criteria. Treat publication and promotion as separate decisions.
