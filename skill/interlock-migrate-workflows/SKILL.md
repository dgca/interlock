# Migrate an Interlock workflow

## Establish the baseline

1. Identify the Interlock instance, workflow ID, and scope of the request. For an audit, use read-only tools and return a plan. For an authorized edit, prepare a candidate for review. Treat publishing and updating callers as separate decisions.
2. Identify what owns the workflow definition. For a workflow built from repository files, find the source files and build or sync command. Use `get_workflow` to read the deployed draft and `draftRevision`. Account for any unpublished changes before editing.
3. Identify the version pins used by callers before reading published definitions. Inspect Workflow nodes, including Batch members and owned children. Check external callers for implicit latest-version starts, response parsers, and checks that depend on node IDs. Record callers you could not inspect. If you need the pinned definitions, save `interlock export WORKFLOW_ID > workflow.json` from the same instance and filter the file locally by workflow ID and version. For a custom engine address, set `INTERLOCK_URL` without the `/mcp` suffix. `list_workflow_versions` returns every retained definition in one response and can exceed client result limits. [Portable bundle contents](https://github.com/dgca/interlock/blob/main/docs/agent-workflows.md#export-and-import-portable-bundles)
4. Check the connected engine version and available tools. Result routing first shipped in 0.2.10. Check each proposed feature against the target instance and use `validate_workflow` with a candidate definition to check support and publication readiness. An editor or CLI running a newer version is insufficient evidence for a different engine.
5. Record representative inputs, routes, outputs, failures, and side effects. Before editing, save a portable bundle as a backup. Reuse the CLI export if you already saved one. Record local test suites separately because portable exports exclude them.

## Choose changes

Read the [branch migration recipe](references/fold-a-branch.md) before deciding whether to fold a Condition or Switch into an Agent, Script, Fetch, or waited Workflow. Classify each candidate as compatible cleanup, intentional behavior change, unsupported, or unnecessary. Prioritize changes by benefit and verification cost. Apply intentional behavior changes only when the user authorizes them.

- **Bindings and defaults.** Preserve downstream field names and types. Use original workflow or item input to carry stable configuration past an Agent. Keep literal dotted keys distinct from nested objects. A default handles a missing field and preserves explicit null, false, zero, and empty text. [Step data and bindings](https://github.com/dgca/interlock/blob/main/docs/node-data.md)
- **Polling Waits and failure routes.** Before replacing a loop with a polling Wait, compare check timing, attempt limits, timeout output, and check side effects. Before adding recovery, check which errors follow the Failed route and which stop the run. Recovery can turn a failed run into a completed run. [Waits and deadlines](https://github.com/dgca/interlock/blob/main/docs/timers.md) · [Failure routes](https://github.com/dgca/interlock/blob/main/docs/failure-routes.md)
- **Saved prompts.** When extracting shared instructions, preserve the composed text and order. A prompt revision can affect future runs of multiple published versions. Identify those consumers before editing a shared prompt. [Saved prompts](https://github.com/dgca/interlock/blob/main/docs/prompts.md)
- **Compact MCP responses.** Audit external clients that read full records from `start_run`, `submit_result`, or `list_work`. Update their reads for summaries or request the explicit full response. [MCP response defaults](https://github.com/dgca/interlock/blob/main/docs/upgrading.md#mcp-response-defaults-in-02)

## Edit and verify

1. For a file-backed workflow, edit the source files and rebuild against the test instance. Use `edit_workflow` on a test copy if you need to try the recipe first. For a library-managed workflow, base the candidate on the current draft to preserve unpublished work. Validate with `validate_workflow` and compare diagnostics with the baseline. For a scoped draft edit, send one `edit_workflow` call with stable IDs and the current `draftRevision`. If the revision is stale or delivery is uncertain, re-read the draft before retrying. Check the saved revision, changed IDs, and diagnostics.
2. Choose the verification method before setting up test cases. Fixture simulation requires published versions and rejects graphs with Wait, Workflow, Batch, or Agent unclaimed timeouts. Use a controlled test for those graphs or for real executor behavior. Compare equivalent cases in an isolated test library. For owned children, import the owner's full bundle into an empty test library and publish the candidate on that imported owner. This preserves ownership and version pins. Bind required variables to local test variables or provision and set them before running. If you stub child calls, report the evidence as parent behavior only. Compare routes, forwarded values, final status, and expected errors. Record gaps. [Fixture simulation](https://github.com/dgca/interlock/blob/main/docs/workflow-simulation.md#supported-scope-and-bounds)
3. Report the workflow ID, baseline version, candidate draft revision, changed and retained nodes, evidence, and gaps. Show which consumers would change when the candidate becomes latest. For authorized publication, recheck the draft revision and validate it immediately before publishing. Update only approved caller pins. Keep the previous published version available for explicit starts or repinning. For callers that always start latest, plan recovery by republishing the prior definition as a new version. Track shared prompt changes separately because a workflow version does not pin the prompt content for future ordinary starts.

See [draft edits and diagnostics](https://github.com/dgca/interlock/blob/main/docs/agent-workflows.md#edit-a-draft-atomically) for MCP arguments and return fields.
